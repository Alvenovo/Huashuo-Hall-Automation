# 运行手册（跑法 + 提权）

各套件怎么跑、提权怎么走。本机 = 唯一执行机（`C:\Users\admin`），只有 C 盘，Python 3.12.10 + `.venv`，只有 Windows PowerShell 5.1（无 pwsh 7），OCR 仅 zh-Hans-CN 引擎。

## 通用约定

- 本机 `python` 不在 PATH，一律用 `.venv\Scripts\python.exe`；跑 python 带 `PYTHONUTF8=1`（或 `-X utf8`）。
- 跑批命令必须带 `.\` 前缀（PowerShell 相对路径）。
- **密码/测试号/微软邮箱只走环境变量，不落盘、不进 git、不写进任何文件。**
- 办公机不要 `--allow-install`。
- 首装初始化慢，本机超时覆盖在 `config.local.yaml`（launch 120 / ready 150），没改入库默认。
- **代理侧能跑什么，由 WorkBuddy 权限层决定，不是项目代码决定**：会话启动参数里 `allowedTools` 只有 `present_files` / `read_me` / `show_widget` / `connect_cloud_service` / `connect_open_platform` / `WebFetch` / `Bash(mcporter:*)`，**裸 `Bash` 不在白名单**，所以代理每跑一条 `git` / `pytest` / `schtasks` 都可能触发一次审批弹窗。另有 `[SandboxCenter] approval=on` + `[SensitiveApproval] listening`，对 `schtasks` / `net share` / `reg` / 防火墙 / 提权这类敏感命令单独弹。**这不是项目 bug，别去代码里找。**
  - **权限配置的权威位置**（不是 `~/.workbuddy-ai/settings.json`，那个只管插件/沙箱白目录）：
    - 用户级 `~/.codebuddy/settings.json` —— 所有项目生效
    - 项目级 `<项目>/.codebuddy/settings.local.json` —— 仅当前项目
    - 语法：`{"permissions": {"allow": ["Bash(git status:*)", "Read", ...], "deny": [...]}}`
    - 内置命令 `/permissions` 可交互式预批准/预拒绝 bash、edit、MCP 工具
  - 本机已放行（2026-09-18）：`Read`/`Glob`/`Grep`/`Edit`/`Write` + git 读写 + `ls`/`pwd`/`date`/`wc`/`file`/`which`/`du` + `pytest` + `.venv/Scripts/python.exe`。**改完下次新会话才生效**（白名单启动时注入）。
  - **故意不全放**：`SensitiveApproval` 对 schtasks/net share/reg/防火墙/提权单独弹，这是产品级安全机制，**关不掉也不该关**——本项目要动计划任务/共享盘/防火墙/提权，正需要人看一眼。也**没有**把 `cat`/`cp`/`echo`/`find` 放进去（分别能读任意文件/覆盖/配合重定向写任意文件/遍历整盘，都不是纯只读）。
- 证据留痕自动生效（所有 pytest 跑批）：跑完看 `reports\evidence\<日期_时间>\report.html`（自包含单文件，可直发组长）。
  **`summary.json` 与 `report.html` 无论什么模式都会写，且列全所有用例**（多机汇总只读 `summary.json`，不读回执）。
  计数分四档：`passed` / `failed` / **`errors`** / `skipped` —— `errors` 是 **setup 阶段就崩、用例没执行**
  （pytest 的 ERROR），2026-09-22 起单独记，别把它当 `failed` 读。
  每用例的原图 `<模块>\<编号>_<标题>\final.png` + `result.json` **只在被采集时才落盘**（用例目录名 = 编号 + 标题，能直接去 `cases/cases.yaml` 对号） —— 开关 `--evidence=all`（默认）
  /`--evidence=failure-only`（只留失败，跑批产物少很多）。
  ⚠️ **默认是 `all`（2026-09-23 改，原来是 `failure-only`）** —— 理由：排查时**通过用例的现场图也有用**
  （"这一步界面长什么样"只能从通过那刻的图看，失败图只有崩掉那一刻）。
  **代价**：每台机器每轮全量档约 650 张图（`unit` 618 条也各一张），比 `failure-only` 多约 150-200MB/轮；
  盘紧张时用 `--evidence=failure-only` 压回去（`reports\` 曾堆到 3.8 万张 PNG）。
  ⚠️ **run 目录本身无论什么模式都会建**（`farm_agent` 靠"前后快照差"认本轮目录，不建就会张冠李戴回传上一轮），
  所以"套件全绿、目录里没图"是**正常**的，不是没跑。
  保留天数 `--evidence-keep-days=30`（0=不清理）。
- **反复弹「Select a credential helper」（GCM 选择框）的根因与修法**（2026-09-18 已修）：`~/.gitconfig` 里 `credential.helper` 的值被写成 **反斜杠转义引号** `!\"<路径>\"`，正确应为普通引号 `"<路径>"`。畸形值让 GCM 每次启动都读不到自己的 helper 选择、于是每次 `git fetch`/`push` 都弹框问一遍（但能读到 Windows 凭据管理器里已存的 token，所以「能用但一直问」）。修法：去掉那对转义反斜杠。GCM 本身用 `git-credential-manager.exe diagnose` 验，7 passed / 0 failed 即健康。
  - ⚠️ **别在终端裸跑 `git credential fill`** —— 它会把明文 token/密码直接打到 stdout。
    只想看非敏感字段就 `| grep -E "^(protocol|host|username)="`。
  - **确实需要 token 时**（典型场景：**本机没装 `gh`、`GITHUB_TOKEN`/`GH_TOKEN` 也没设**，
    但要调 GitHub API，比如改仓库可见性）——可以在脚本里
    `subprocess.run(["git","credential","fill"], input="protocol=https\nhost=github.com\n\n", capture_output=True, text=True)`
    接住，**只回显长度和前 4 位**，绝不 print 全文。2026-09-22 就是这么把仓库转 private 的：
    `PATCH https://api.github.com/repos/<owner>/<repo>`，body `{"private": true}`，
    头 `Authorization: Bearer <token>`。
  - **复核可见性**：匿名 `GET /repos/<owner>/<repo>` 返回 **404 = 已是 private**；返回 200 且带
    `"visibility": "public"` = 还公开着。**别只看 commit message** —— `b346b62` 写着"仓库转 private 后"，
    但 2026-09-22 一查 `private: false`，中间又被公开回去了。
  - ⚠️ `diagnose` 会在**当前目录**生成 `gcm-diagnose.log`（含敏感信息），跑完必须删。

## 提权怎么跑（本机已验证的路）

- 代理侧无法自我提权：自己建 `/RL HIGHEST` 计划任务被拒绝访问；键鼠注入进不了交互桌面（只能截图）。UAC 的「是」画在安全桌面上，非提权进程碰不到 —— 这是唯一绕不过去的硬墙。
- **为什么 P1-A 必须提权**：夹具应用（网易云音乐）要写 `C:\Program Files\NetEase\CloudMusic` 和 HKLM 卸载表。另外厂商**卸载器本身也是提权进程**（实测 pid 1996 `TokenElevation=1`），非提权点不动它。
- **UIPI 的边界（实测）**：非提权进程对提权窗口，`WM_GETTEXT`/`WM_GETTEXTLENGTH` **放行**（在 UIPI 的消息白名单里），所以控件文字读得到；`BM_CLICK`、`SetForegroundWindow`、`PrintWindow` **被挡**，所以点不动、也前置不了。表现就是「读得到、点不动」—— 别把读得到误判成能自动化。想给提权窗口截图 OCR，必须在提权进程里先 `SetForegroundWindow` 再抓屏（非提权抓下来的是挡在它前面的窗口，OCR 会读出编辑器里的字）。

### 提权通道（2026-09-23：从「手工开管理员窗口」改成 broker）

**一句话**：非提权的农场 agent 写一个请求文件 → 触发计划任务 `HallAutoP1` → 提权侧读请求跑套件 → 写结果文件。跑批时**零人工**。

**为什么不能把 agent 整体提权**：会改掉 `launch` / `login` 那批用例的权限上下文（见上面 UIPI 那条）。所以 agent 保持非提权，只有 `install` / `apps-lifecycle` 这两类走通道。

**为什么参数走文件**：计划任务的「操作」字段是一段**固定字符串**，传不了命令行参数
（`学习库/07-用例与断言策略/03-标记体系与门禁.md` 记着这条坎，也是当初把提权段做成手工步骤的直接原因）。

```
reports/_elev/request.json      非提权侧写（原子写：先 .tmp 再 replace）
reports/_elev/result.json       提权侧写（按 request_id 认领，不按「文件在不在」）
reports/_elev/elevated_run.log  提权侧的 pytest 输出
reports/_elev/wrapper.log       计划任务动作脚本自己的输出
```

**协议常量与校验的唯一出处**：`hall_auto/elevation.py`（任务名、脚本名、路径、参数白名单、`is_elevated()`）。
**提权侧主体**：`tools/elevated_runner.py`；**计划任务的动作**：`tools/run_elevated_suite.ps1`（薄壳，只定位仓库并启动 Python 主体）。

**计划任务 `HallAutoP1`**（bootstrap 第 11 步建，`/RL HIGHEST`）：

```powershell
# 触发（普通权限即可，0 人工）
MSYS_NO_PATHCONV=1 schtasks /Run /TN HallAutoP1
# 核一眼动作指向（必须是 run_elevated_suite.ps1，不是老的 run_p1_apps.ps1）
schtasks /Query /TN HallAutoP1 /XML
```

⚠️ **Git Bash 里 `/Run` 会被当路径转换**，命令行手敲必须写 `MSYS_NO_PATHCONV=1`。
Python 走 `subprocess` 传参数列表没有这个问题 —— 这也是走 broker 比让人粘命令稳的地方之一。
⚠️ **指向旧动作 `run_p1_apps.ps1` 的任务必须重建**：它只会跑夹具装卸，
新加进全量档的 `install` 永远跑不到，且不报错。bootstrap 检测到这种情况会**主动覆盖重建**
（唯一一处「默认不重建」的例外，理由写在 `step_schtask` 的 docstring 里）。
⚠️ **幂等**：同一份请求被触发两次时，提权侧看到结果文件里的 `request_id` 已经是它 → 直接退出，不重复跑。
真装真卸跑两遍会白等十几分钟还搅乱机器状态。

**手工排查提权段**：

```powershell
# 首选：一条命令判掉 5 条分支（在**节点**上跑 —— _elev 是节点本机目录，控制机看不到）
.\.venv\Scripts\python.exe -X utf8 tools\check_elevation.py

type reports\_elev\elevated_run.log     # pytest 输出
```

`schtasks /Run` 返回 0 只代表「请求被接受了」，**不代表任务真启动了** —— 任务被触发却
什么都没发生是完全可能的，而且**节点侧一句报错都没有**。症状与控制机侧「日志停在
投任务那一行」同形，**两边都像死机**。
**2026-09-29 起 farm_agent 不再干等 4 小时**：触发后 60s 内提权侧毫无动静（`wait_elevated_started`）
就 fail-fast 退出码 2，并打出下面这张表的排查清单。`check_elevation.py` 也能手动按
「产物优先于计划任务查询」的顺序判掉这些分支：

| 现象 | 结论 |
| --- | --- |
| **节点是笔记本、拔着电** | **头号真因（2026-09-29 实测卡一整天）**：任务默认 `DisallowStartIfOnBatteries=True`（「不用电池启动」），拔电时调度器**只排队不启动**（`schtasks /Query /V` 显示「模式: 已排队」），`/Run` 仍返回 0。修法见下方「坑 20」 |

### 坑 9：pytest 临时目录的**两种**崩法 —— 共享目录被污染（238 条 ERROR）/ 父目录不存在（219 条 ERROR）

> 症状都是「**凡是用了 `tmp_path` 的用例全 ERROR**，报告上像代码烂了」。
> 形态 A（2026-09-23，管理员跑过 → ACL）：本节正文；
> 形态 B（2026-09-28，新机没有 `reports/_pytest_tmp/` → `FileNotFoundError`）：见下面「形态 B」。

**症状（形态 A）**：新机第一次跑农场，`unit` 套件报 **238 / 599 条 ERROR**，全是
`PermissionError: [WinError 5] 拒绝访问。: 'C:\Users\<用户>\AppData\Local\Temp\pytest-of-<用户>'`。
报告上看着像"代码烂了"，实际**一条都不是代码问题**。

**根因**：pytest 默认把临时根放在 `%LOCALAPPDATA%\Temp\pytest-of-<用户>`，**按用户名复用**。
而 bootstrap 第 12 步的自检是**用管理员**跑的（bootstrap 整体要管理员）——
Windows 把**提权进程创建的对象的 owner 记成 `BUILTIN\Administrators`**，ACL 也只给
Administrators 全控（pytest 建这个目录时带 `mode=0o700`，等于关掉了继承）。
之后**普通权限**跑 `tests/unit` 时，进程令牌里的 Administrators 是 **deny-only**
（UAC 过滤令牌的标准行为）→ 在它里面建子目录被拒 → 凡是用了 `tmp_path` 的用例在
setup 阶段全崩。**每台新机跑一次 bootstrap 就污染一次**，不是"清一次就好"。

**修法（已落地）**：不再用那个共享目录。

- `hall_auto/suites.py::pytest_basetemp()` —— 每次运行一个**专属**的
  `reports/_pytest_tmp/<任务>_<套件>_s<分片>_p<pid>_<时间戳>`，谁建的谁用，永不复用。
  带 pid + 时间戳是因为 pytest 对 `--basetemp` 会先 `rm_rf` 再 `mkdir`，
  复用路径而归另一个身份所有时 **`rm_rf` 本身就抛异常**。
  ⚠️ **父目录要自己建**：pytest 的 `--basetemp` 只做一层 `mkdir()`（不带 `parents=True`），
  父目录不存在会直接 `FileNotFoundError` —— 症状与上面**长得一模一样**，很容易查错方向。
- `build_command()` 一律加 `-p no:cacheprovider`：`.pytest_cache/` 有同样的 ACL 问题
  （管理员建过之后普通权限写不进，每轮打一堆 `PytestCacheWarning`）；我们一条都不用
  `--lf/--ff/cache` fixture。
- bootstrap 第 12 步的自检 + 它的「换进程重跑」都带同一套隔离参数
  （`bootstrap_machine._selftest_isolation()` —— **函数，不是常量**，理由见下面「形态 B」）。
- `farm_agent` 取到任务时顺手清过期的 basetemp（尽力而为，删不掉不影响正确性）。

守卫：`tests/unit/test_suite_planning.py` / `test_bootstrap_policy.py` / `test_elevation.py`。

#### 形态 B：父目录在新机上不存在 → **219 条 ERROR**（2026-09-28，`LAPTOP-68TGB8VB`）

上面那条 ⚠️「父目录要自己建」**当时只写在文档里，代码没做**：bootstrap 那侧把隔离参数写成了
**模块级常量** `SELFTEST_ISOLATION`，而**常量建不了目录** —— 而这条知识在
`hall_auto/suites.py::pytest_basetemp()`（函数，里面有 `PYTEST_TMP_ROOT.mkdir(parents=True)`）里
**本来就写着**，只是没被这条路用上。

**为什么本机看不出来**：`reports/` **整个在 `.gitignore` 里** —— 新机 clone 下来压根没有
`reports/_pytest_tmp/`，而本机早被农场跑批建出来了。**本机假绿，每台新机必红。**

- 真机症状：第 12 步自检 `2 failed, 434 passed, 1 skipped, 219 errors in 13.49s`，
  屏幕上只有一行被截断的 `FileNotFoun...`（`SELFTEST_MAX_LISTED` 只列前 12 条）。
  第一行是 `ERROR tests/unit/test_apps_policy.py::test_fixture_apps_parsing - FileNotFoun...`。
- **本机精确复现（把修复回退 + 删掉 `reports/_pytest_tmp`，用同一组参数跑）：
  `438 passed, 221 errors` —— 与新机那行「失败 221 条」逐字对上**
  （新机 656 条 = 219 ERROR + 2 FAILED；本机 659 条 = 221 ERROR，多出的 2 条是本轮新加的
  两条守卫用例自己也用 `tmp_path`；新机那 2 条 FAILED 在本机是绿，因为本机用户名叫 `admin`）。

#### 为什么是 219 条，不是 656 条？—— 这个「边界」本身就能定位根因

`tests/unit/test_suite_planning.py` 里有几条用例调 `suites.pytest_basetemp()`，
而**那个函数自己会 `PYTEST_TMP_ROOT.mkdir(parents=True, exist_ok=True)`**；
这几条用例**不用 `tmp_path`**，所以在父目录缺失的那一轮里**照样跑得过** ——
一旦跑到它们，父目录就被建出来了，**后面的用例全部转绿**。

所以两个可复用的诊断特征：

1. **"一大片 ERROR + 后面一批全绿"** → 根因是**某个用例中途把缺的东西建出来了**，
   报错清单的**最后一条**就指在那个"肇事"用例附近（本例最后一条 ERROR 落在
   `test_security_parse.py`，下一个文件就是 `test_suite_planning.py`）。
2. **"换进程重跑只剩几条"** → 因为重跑时**父目录已经被建出来了**，219 条自然转绿，
   只剩真正确定性的那 2 条。**别把"重跑剩得少"读成"偶发 flake"。**
   （顺带说明：`pytest` 的 `getbasetemp()` 在抛异常前**不会**缓存失败结果，
   所以下一次 `tmp_path` 请求会**再试一次** `mkdir` —— 父目录一出现就立刻恢复。）
- 修：常量 → `_selftest_isolation()` 函数，进去先 `PYTEST_TMP_ROOT.mkdir(parents=True, exist_ok=True)`；
  建不出来时 `step_selftest` **翻成一句人话并判失败** —— 不许让 219 条 `FileNotFoundError` 代替报错。
- 守卫：`test_selftest_isolation_creates_its_basetemp_parent`（**先把父目录删掉再验**，靠"跑一遍看看"验不出来）、
  `test_selftest_reports_when_the_basetemp_parent_cannot_be_created`。两条都验过负路径会红。

**通用教训（比这条坑本身值钱）**：

1. **有副作用的初始化不能写成常量** —— 常量没有执行时机，`mkdir` 就没地方放。
   （同一个毛病的另一种形态：docstring 里写了约束、代码却不检查 —— 见《问题与解决.md》第 7 条。）
2. **本机绿 ≠ 新机绿**：凡是"本机碰巧有、新机不会有"的东西（`.gitignore` 掉的 `reports/`、
   `.venv`、`config.local.yaml`），验收时必须**先把它删掉再跑一遍**。
   —— 这正是《交付前验收.md》要抓的那一类。

### 坑 10：失败文本被截断，只留头 → 把根因丢掉（2026-09-23）

### 坑 12：短信验证码被服务端限流（2026-09-23，2026-09-28 补「按钮回来 ≠ 放行」）

**症状**：`test_forgot_password_reset_manual` 报
`忘记密码：连点 N 次「发送验证码」，CodeSendBtn 都没进倒计时态`。

**根因**：短信验证码是**服务端限流**的。短时间内给同一个号发太多次，服务端拒绝发送，
界面上通常只闪一下提示（**截图抓不到**），按钮留在原位不动 ——
表现与"点击没落上"**完全一样**。原来的报错只说「可能没触发」，
一线会去查控件、查 UIA，方向全错。

⚠️ **「按钮回到控件树」不等于「服务端放行」**（2026-09-28 真机实付）：倒计时是**页面自己**的
UI，重新进这一页就重置了；限流在服务端（常为 60s）。还原程紧接第一程再发，
必然落在那个窗口里 —— 原来「点一次 + 等 8s 就判死」，等于这条用例的第二程**注定失败**。
**修法（两条）**：

1. `request_forgot_sms` 在 `CODE_SEND_RETRY_SEC`（75s）窗口内**反复点**；
   点中的那一次按钮会进倒计时态、直接返回，所以不会多点、不会多发短信。
2. 报错里把「短信发送超限」写在第一条并给出动作（换号 / 等冷却）+ 连点次数。

⚠️ **不要把它改成 skip** —— 「点击真没落上」也是产品缺陷，转成 skip 会把真 bug 盖掉。
连点多次都不动才是强信号；**一次都没点动**是另一条报错（那是控件/UIA 问题，不是限流）。
⚠️ 这条用例要**连发 2 个码**（重置 + 还原），是全部用例里最容易撞上超限的一条；
**调试期反复重跑会把它自己逼到限流**。

#### 坑 12 补：限流的**实测证据**与**我们不知道的部分**（2026-09-28）

被问「一个测试号能不能一直跑」时，先分清**测到的**和**猜的** —— 别把估计当实测：

**实测（09-28 那轮 `login-manual`，同一个号）**：

| 时刻 | 第几条 | 结果 |
| --- | --- | --- |
| 14:47:10 | 第 1 条（短信登录） | ✅ 发出、收到、登录成功 |
| 14:47:55 | 第 2 条（重置，距上一条约 45s） | ✅ 发出、收到、改密成功 |
| 14:48:13 | 第 3 条（还原，距上一条约 18s） | ❌ 服务端拒绝，按钮不进倒计时态 |

**由此能确定的**：
- 是**发码请求**被拒（服务端压根没发），不是"手机收码有次数限制"。
- 间隔 45s 能过、18s 被拒 → **不是"每条固定间隔 60s"** 那种简单规则，更像**窗口内计次**。
- UI 上那个 60s 倒计时是**客户端**的（`CODE_RESEND_TIMEOUT_SEC=65` 就是从它来的），
  **重进页面就重置**，跟服务端的限制**不是一回事**。

#### 坑 12 补二：限流是「手机号 × 业务场景」双维度（2026-09-28 17:xx 探针实测）

一次性探针实测（信号口径同坑 12：点发码后 `CodeSendBtn` 进倒计时=受理、连点不进=被拒；
**每次填号后读回校验输入框**，排除"残留上一个号"造成的假结论 —— 探针未入库）：

| 时刻 | 号 | 入口 | 结果 |
| --- | --- | --- | --- |
| 17:26 / 17:31 / 17:37 | 号1 | 忘记密码 | ✅✅✅（各隔 5-6 分钟） |
| 17:38:52（+70s）/ 17:39 | 号1 | 忘记密码 | ❌❌ |
| 17:44:05（距上次 ✅ 约 6 分钟） | 号1 | 忘记密码 | ❌ |
| **17:46:00（同上一行仅隔 2 分钟）** | **号1** | **短信登录** | **✅** |
| 17:27 / 17:30（单独测） | 号2 | 忘记密码 | ❌❌❌❌ |
| 17:34:00 | 号2 | 短信登录 | ✅ |
| **17:52→17:53** | **号2** | **短信登录（真提交码）** | **✅ 登进，用户区昵称=号2 手机尾号** |
| **17:54:42（登录后）** | **号2** | **忘记密码** | **✅（登录前 17:27/17:30 还是 ❌）** |

**锁定的结论**：
- **维度 = 手机号 × 业务场景**，**不是**设备/IP：同一台机、同一时间窗，号1 能发号2 不能 →
  排除设备/IP；号1「忘记密码被拒、2 分钟后短信登录却放行」→ **两个场景各是一套独立配额**。
- **忘记密码要求账号已注册**：号2 登录前忘记密码连拒（17:27/17:30），**短信登录登进后**
  （17:53，用户区昵称=号2 手机尾号）忘记密码**立刻能发**（17:54）—— 证明号2 原先**未注册**，
  短信登录把它**注册/激活**了。⚠️ 所以"忘记密码发不出"不一定是限流，**也可能是号没注册**，
  两者表现一样；**先拿这个号走一次短信登录激活，再走忘记密码**即可区分/解决。
- **忘记密码场景有两道闸**：① **短窗口**——上一条成功后约 60s 内再发被拒
  （14:48 那条 +18s 被拒，当时当天才发 1 条，是短窗口不是日限）；② **当天累计上限**——
  号1 今天发到第 4 条后，连隔 6 分钟也拒（17:44 实锤），且**恢复按小时计**
  （14:48 被拒 → 17:26 才又成功，约 2.6h）。报错里「十几分钟到次日」的**"小时/次日"方向对，
  "十几分钟"偏乐观**。
- **短信登录场景**配额独立：忘记密码被打爆**不影响**短信登录（号1 17:46 实证）。
- 对 `test_forgot_password_reset_manual` 的直接含义：它一趟要**连发 2 条忘记密码码**（重置 + 还原）。
  还原那条离重置只隔约 20s，**落在 60s 短窗口里**——这正是 09-28 14:45 那轮还原程失败的真因。
  ⚠️ 那轮跑的是**旧代码**（报错还是「点发送后 CodeSendBtn 没消失，可能没触发」单点判死版）；
  **现版 `request_forgot_sms` 已在 75s 窗口内反复点**（`CODE_SEND_RETRY_SEC`），能盖住 60s 短窗口，
  所以**测试机 `git pull` 到新代码后，还原程的短窗口问题应自愈**；剩下的硬约束是**当天累计上限**
  （每号每天约 4 条忘记密码码 = 往返用例约 2 趟/号/天）。

**仍不知道的（别当结论说）**：
- 忘记密码当天累计上限的**精确条数**（号1 今天约发到第 4 条到顶，但受上午那轮干扰，不是干净值）。
- 短窗口的**精确秒数**（已知 >18s、≤5min，疑似就是 60s，与客户端倒计时同值，但没干净测过）。
- 连续输错码会不会触发**账号锁定**（`CODE_MAX_ATTEMPTS` 注释提过）—— 仍未验。

⚠️ **还原程失败必须报出「账户可能停在【新密码】」**（2026-09-28 补）：
限流发生在**还原那程**时，第一程（改成新密码）**已经成功了** —— 账户真的被改了。
原来只有「人放弃还原」那条分支写这句话，`request_forgot_sms` 自己抛错会**绕过**它，
现场只看到一句限流提示，一个字都没提密码。现在 `_report_restore_failure` 兜住所有
还原程异常；用例本来就已失败时不盖原报错，只在日志里补一句警告。

### 坑 13：用户区显示的不是登录手机号尾号 —— **用户区显示的是「账号昵称」**（2026-09-28 更正）

**症状**：`test_password_login_success` / `test_sms_login_manual` 断言 `user[-5:] in name` 失败：

```
AssertionError: 已登录态的用户区没带登录手机号的尾号：显示 '用户信息区域，已登录用户：asus_1883771273'，期望含 '61935'
```

**定性（2026-09-28，截图实锤）**：用户区显示的是**账号昵称**。
`1883771273` 只有 **10 位**，不是合法的国内手机号（11 位、1 开头）——
所以 2026-09-23 那条「用户区显示的是**绑定号**」的定性**是错的**：
那轮"换个测试号就过了"，只说明**另一个号的昵称恰好是手机号**，证明不了显示的是绑定号。

**断言的真实前提（历史）**：`user[-5:] in name` 实际在断言「**这个账号的昵称里含登录手机号的尾号**」。
那是**账号数据**，不是产品不变量（昵称用户随便改），所以它随账号变红、是"假红发生器"。

会"登录成别的号"而无人抓——真机没见过，属推测；哪天撞见再补显式期望昵称。

⚠️ 登录本身是**成功**的：`logged_in()` 已经过了，用户区也读到了文案。

### 坑 15：大厅被别的窗口挡住 → 同步页列表刷不出来 / 微软登录进不去（2026-09-23）

**症状**（两条同时出现，且**截图里大厅完全没露出来**，只有微信 + PowerShell）：

- `test_sync_list_logged_in`：`AppListState(tab='sync', loaded=False, needs_login=False, items=())`
  → `登录后同步页仍没刷出列表（NoAppListBox 没出现）`，等满 45s 超时。
- `test_microsoft_login_sso`：`微软登录：提交后未进入已登录态`，等满 40s 超时。

**关键线索**：`needs_login=False` 说明**登录态是有的**（不是"没登录"），
只是**列表一直没渲染**；而两张失败截图**一模一样**，都是微信 + PowerShell 在前台、
**大厅一个像素都没露**。

**机制**：大厅的主内容区是 **WebView2**。窗口被完全遮挡时 Chromium/WebView2 会
**暂停渲染**（省电策略），于是依赖渲染结果的断言永远等不到 —— 而 Win32 那层控件
（按钮、标题）照样读得到，所以"能读、但页面是空的"。

**做法**：
- **跑批期间把无关窗口最小化或关掉**（微信、QQ、编辑器、其它 PowerShell）——
  尤其是**别让它们压在大厅上面**。
- 本用例的前置检查里已经有「把无关窗口最小化」这一条，**别当可选项**。
- 失败截图里看不到大厅 = **先怀疑遮挡**，别去查产品。

**已做成自诊断（2026-09-23）**：`hall_auto/winapi.py::occlusion_hint(pid)` ——
用 `WindowFromPoint` 在主窗的中心 + 四角采样，谁不是大厅进程的窗口就算遮挡，
把**窗口标题 + 机制 + 动作**直接拼进失败信息。已接在两处：

- `tests/launch/test_p1_apps.py::test_sync_list_logged_in` 的断言
- `hall_auto/login.py::wait_microsoft_logged_in` 的报错

所以**下一次不用再逐张看截图**，报错里会直接写「大厅被别的窗口挡住了：「微信」…」。

⚠️ **判定必须按 pid 过滤**：大厅自己的登录 / 绑定弹窗是**独立顶层窗**，
盖在主窗上是这些用例的**常规状态**。不过滤的话会把正常状态误报成遮挡 ——
报错指错方向比没有报错更糟。守卫：`tests/unit/test_winapi_occlusion.py`（注入法验红过）。

⚠️ **「窗口不在屏幕上」也是同一类，而且更容易被藏住**（2026-09-23 真机第二轮）：
`test_sync_list_logged_in` 等 44s 后报「登录后同步页仍没刷出列表」，而**遮挡提示返回空**、
失败截图里**大厅整个不在屏幕上**（只有桌面 + 终端）。原因是 `occlusion_hint` 当时只判了
「被别的窗口挡住」，没覆盖「窗口被隐藏 / 缩到托盘」—— 主窗不可见时它直接返回空串。
现在四种状态都覆盖了：**被挡 / 最小化 / 不可见 / 连顶层窗都没有**。

**并且做了正面修法**：`hall_auto/winapi.py::ensure_window_shown(hwnd)` 在
`launch.wait_main_window` 找到主窗后调用 —— 窗口正常时**一个动作都不做**，
只有最小化 / 隐藏时才 `SW_RESTORE` / `SW_SHOW`，并把"修了什么"打进日志（不静默）。

**为什么必须修在启动阶段**：**UIA 找得到隐藏 / 最小化的窗口**，所以
`wait_main_window` 会"成功"、测试继续往下跑，而 WebView2 不渲染 ——
最后报成「列表没刷出来」这种**看着像产品缺陷**的错。等断言失败后再猜就晚了。

### 坑 15 补：**DWM cloaked** —— 唯一能解释「API 说可见、屏幕没画」的机制

真机最后一击（2026-09-23 16:47）：诊断报

```
窗口状态：pid=22356 hwnd=0x2B0A1A rect=(346, 209, 2214, 1331)
visible=True iconic=False cloaked=? 采样命中大厅自己 5/5 遮挡=无
```

而失败截图里**大厅一个像素都没画出来**（只有终端和豆包）。前四种状态全排除 ——
只剩 **DWM cloaked**：**在另一个虚拟桌面上的窗口、以及被挂起的 UWP 窗口都会被 cloaked**。
这类窗口：

- `IsWindowVisible` 返回 **True**
- `WindowFromPoint` **照样命中**它（z 序上确实在上面，采样全落在它自己身上）
- 但**屏幕上根本不画** → WebView2 不渲染 → 依赖页面的断言永远等不到

**所有"可见性"检查都说正常，只有 `DwmGetWindowAttribute(DWMWA_CLOAKED)` 说不对。**

- `winapi.window_state_facts()` 现在会打 `cloaked=N`；`occlusion_hint()` 单列这一种状态；
- `ensure_window_shown()` **不装作能修** —— `ShowWindow` 管不着 cloaked，
  它只报事实（装作修好会把真因盖掉）。
- **处理**：把大厅切回**当前虚拟桌面**（或先关掉多桌面）再重跑。

守卫：`tests/unit/test_winapi_occlusion.py`（20 条，含"不许装作修好"）。

### 坑 15 再补：**alpha=0 的完全透明分层窗口** —— 真机最后剩下的那一种

加上 cloaked 判定后再跑一轮，依据变成：

```
visible=True iconic=False cloaked=0 采样命中大厅自己 5/5 遮挡=无
```

**`cloaked=0`** → 虚拟桌面也排除。**五种状态全部排除**，而截图里大厅仍然一个像素没画。

### 坑 16：微软账号那个号没绑手机号 → SSO 后弹「绑定手机号」（2026-09-23）

**症状**：`test_microsoft_login_sso` 超时 40s，报 `微软登录：提交后未进入已登录态`；
**遮挡诊断返回空**（不是遮挡）。现场看到的是：脚本把「绑定手机号」弹窗关掉了、却没点「发送验证码」。

**根因**：微软账号登录用的是**另一个账号**（绑到微软账号的那个），它**没绑过手机号** →
SSO 成功后弹「绑定手机号」。**绑定是登录的必填一步**，不绑就回不到已登录态；
而 `wait_microsoft_logged_in` 只会死等 → 40s 超时 → 报「提交后未进入已登录态」，
**把「这个号没绑手机号」这个真因盖成了"登录失败"**。

**修法**：把「绑定手机号」当成**第 4 个「需人工」分支**（前三个是 password / mfa / email_otp），
**skip 而不是 fail** —— 这本来就是这条用例自己写的设计边界，只是漏了绑定这一种。
- 判据放在 `wait_microsoft_logged_in` **之前**（`find_bind_dialog`，等 8s），
  且**先 `dismiss_bind_dialog` 再 skip**：弹窗是模态的，留着会把后面每条用例都点不动。
- 收码 + 绑定流程在 `test_microsoft_login_code_manual`（`-m manual`）。
- **根治办法**：手工把微软账号绑一次手机号，之后**这台机器**上这条就能无人值守跑通。
  ⚠️ **2026-10-10 实测：绑定按机器生效（不跨机器）** —— ①同一台机器绑一次之后，
  再登录**不再弹**；②换新测试机**仍会弹**（用户两遍复核）。所以它是**每台新机各做一次**
  的动作，**别假设"绑一次全局生效"**。新机上线时按本机确认一遍：不弹 = 已生效；
  弹 = 在这台机器上绑一次（做法见《新机操作清单.md》）。

⚠️ **不要因为这条就把 `test_microsoft_login_sso` 整体挪进人在环**：绑过号之后，
SSO 免密路径确实能无人值守跑通（09-16 探针实跑过「SSO 后用户区=已登录用户 61935」）。
挪走会白丢一块覆盖；**skip 分支已经表达了同一件事**（需要人时明确说"需要人"）。

## 多机跑批（2026-09-18 落地）

### 三步上手

```powershell
# 1) 每台新机器铺环境（管理员 PowerShell）。若要连共享盘取包，先设凭据
$env:HALL_SHARE_USER="hallshare"

# 铺完后填节点凭据文件（见下「节点凭据通道」），bootstrap 只生成空模板

# 2) 控制机：设农场目录（共享盘）并投任务
$env:HALL_FARM_ROOT = "\\SHARE\qa\hall-farm"
.\.venv\Scripts\python.exe -X utf8 tools\farm_control.py dispatch --nodes R01,R02,R03 --suites launch,apps-detect

# 3) 节点机：取任务执行（计划任务里用 --loop 常驻，或 --once 单次）

```

控制机侧还有 `status`（看进度）、`aggregate`（出「节点 × 用例」矩阵报告）、
`prune`（清 `done/` 的老回执）。

⚠️ **`done/` 不是"已完成"的展示而已，别手工删光** —— 它还是**凭据状态的兜底来源**
（`_node_creds_from_receipts`：证据目录里没有 `node_env.json` 的老节点靠读它）。
删光了那些节点的「凭据」列会**全变 ✗**，一线会拿着全红的凭据列去反复折腾 `farm_node.env`
（2026-10-12 修过的坑）。而兜底函数**按 mtime 只取每个节点最新的一份**，更老的永远读不到 ——
所以 `aggregate` 收尾会自动跑一次清理（**每节点保留最新 3 份**），也可以手动 `prune`。
2026-10-13 实查：共享盘上 48 份回执全是同一个节点、跨 09-29~10-10，清掉 45 份。

⚠️ **节点机两条命令的正常输出，别误判成故障**：
`--once` 打「无任务，退出」= **链路通了**，只是控制机还没投任务；
`--loop` 空闲时**每 30 秒打一行心跳**（`[HH:MM:SS] 轮询 #N：无任务…`）——
**它在正常空转，不是卡住**。真取不到任务时那行会换成中文排查指引，见「节点侧的四道防呆」。

投 `login` / `login-manual` 套件前，`dispatch` 会检查凭据环境变量，缺了就告警（不阻塞）。

```powershell
# 等价的老路（只投不等）

```

全量档 = `unit, launch, apps-detect, login, settings, security, wb, wb-install, apps-lifecycle, install`
（唯一定义在 `hall_auto/suites.py` 的 `FULL_RUN_SUITES`，dispatch 会把展开结果打出来）。
**刻意不含**：只有 `login-manual`（人在环，`farm_safe=False`，永不进无人值守农场）。

**2026-09-23 起 `install` / `apps-lifecycle` 进了全量档** —— 它们要管理员，但走的是
提权通道（见上面「提权通道」），**节点侧零人工**。之前的结论「farm_agent 非提权 → 投了必挂」
过时了：提权通道早就建好，只是没人接上；不接的代价就是跑批被切成「全量档 + 开管理员窗口补跑」两段。

会把这次要真装真卸的套件**逐条打出来**，并且只能投给测试机。

守卫：`tests/unit/test_farm_agent_policy.py::test_receipt_is_written_before_the_manual_prompt`。

人在环的产出走**独立回执** `done/<node>_<task_id>_manual.json`，不和自动段那份混在一起 ——
两份合一的话，「自动段跑完了没有」和「人在环跑完了没有」在文件层面分不开。
跑完在控制机补一次 `aggregate` 把结果并进报告。

⚠️ **只有任务覆盖全量档（9 个套件）时才问。** 原来任何任务跑完都问 ——
投一个 36 秒的冒烟任务，节点也会弹问句并永久 `input()` 阻塞，**控制机侧只看到「执行中」不动，
与节点死机同形**（真机踩到：`launch` 4 passed / 36.9 秒就跑完，之后两分多钟毫无动静）。
想在任何任务后都问（手工调试）→ 加 `--ask-manual`；想永远不问 → `--no-manual`。

| 顺序 | 用例 | 要什么 |
|---|---|---|
| 1 | `test_microsoft_login_code_manual` | 1 个邮箱验证码（发到 `HALL_MS_USER` 那个邮箱）；**没绑过的账号再加 1 个绑定短信码** |

「绑定短信码」见下面《登录后「绑定手机号」弹窗》—— **只有没绑过的账号才弹**，
绑过一次之后 1、2 两条就各只收 1 个码。

**⚠️ 微软那条不止要邮箱码**（2026-09-22 用户指出）：邮箱验证通过、登录成功后，
没绑过号的账号照样会弹绑定弹窗 → 脚本自动填号 + 自动点「获取验证码」→

|---|---|---|
| 首次跑（没绑过号） | 4～6 | 邮箱 1 + 短信 1 + 绑定短信 1～2 + 忘记密码 2 |
| 已绑过号 | 4 | 邮箱 1 + 短信 1 + 忘记密码 2 |

`_MANUAL_BIND_WARNING`，终端提示语从它们打出来。守卫会拿 `test_p1_login.py` 里
`-m manual` 用例的**真实文件顺序**去对（`tests/unit/test_farm_agent_policy.py`）——
**改用例位置，提示语必须跟着改**，否则人照着错的顺序准备（原来就把「短信登录」
写在「微软登录」前面，人先掏手机、第一条要的却是邮箱码）。

**门禁有两道，都过才问**：① **人能看见 + 能回答**（`stdin` 与 `stdout` **都**是终端）；
② **任务本身覆盖全量档**（`task_covers_full_run`）。开关只能**额外**放开或关掉：
无人值守节点上问了没人答，agent 会永久卡在 `input()`，而控制机只看到「执行中」——
与节点死机同形，是最坏的一类挂起。计划任务里要显式关掉加 `--no-manual`。

**只跑人在环**（不走农场）：
```powershell
.\.venv\Scripts\python.exe -X utf8 tools\farm_agent.py --local login-manual
```
`--local` 对 `interactive=True` 的套件自动走交互模式（stdout 不重定向），提示语才到得了终端。

#### ⚠️ `-s` 必须带上，而且不能靠人记得（2026-09-22 真机踩出）

pytest 默认捕获会把 `sys.stdin` 换成 `DontReadFromInput`，于是 `sys.stdin.isatty()` **恒为 False** ——
三条人在环用例**一句不落地全 skip**，而 `farm_agent` 照打「退出码 0」，看着像
「跑过了、只是没到条件」，**实际是这套功能从没执行过**。
就算绕过那个守卫，`input()` 也会抛
`OSError: pytest: reading from stdin while output is captured! Consider using -s.`

实测对照（同一台机、同一条探针用例）：

| 模式 | `type(sys.stdin)` | `sys.stdin.isatty()` | `input()` |
|---|---|---|---|
| 默认捕获 | `DontReadFromInput` | `False` | 抛 `OSError` |
| 加 `-s` | `TextIOWrapper` | `True` | 正常读 |

所以 `-s` 由**套件定义**自己带（`hall_auto/suites.py` 的 `build_command`，
`login-manual` 标了 `interactive=True`）—— 走 `farm_agent --local login-manual` 自动就有；
**手敲 pytest 必须自己加**。

#### 点完「发送验证码」自动把终端提到最前

脚本操作大厅时会把大厅窗口顶到前台，终端被压在后面 —— 每收一个码都要 Alt+Tab 切一次。
所以**每个 `input()` 之前都会先把终端抢到前台**（`hall_auto/console.py` 的 `focus_console()`）：

- 三条找窗口的路，按可靠性排序：`GetConsoleWindow()`（经典 conhost）→
  `GetConsoleTitleW()` + `FindWindowW()`（Windows Terminal 与 conhost 都覆盖）→
  沿**父进程链**枚举顶层窗（终端被包在 VS Code 之类壳里时的兜底）。
- `SetForegroundWindow` 单独用**没用**（Windows 前台锁），要配 `AttachThreadInput`
  借当前前台窗口的输入线程资格，调完再摘掉。
- **桌面/任务栏窗口被显式排除**（`Progman` / `WorkerW` / `Shell_TrayWnd`；爬链遇
  `explorer.exe` 就停）—— 不排就会把桌面提到前台 = **所有窗口最小化**，比不聚焦还糟。
- **拿不到窗口返回 `False`，绝不抛** —— 这只是省一次 Alt+Tab 的便利，
  不是用例的前置条件，也不是任何断言的一部分。
- 人在环用例里**只许通过 `_ask_code()` 读 stdin**（那一处负责"先切窗口再问人"）。
  散着写 `input()` 会漏掉切窗口，而且**不报错**，纯静默降级 ——
  守卫用 AST 检查：`tests/unit/test_manual_loop_policy.py`。

#### 验证码输错了在**原地重输**，不重发码、不重跑（2026-09-28）

**行为**：码提交后被拒（页面还停在输入态）时，脚本**再问一次**，最多 3 次
（`hall_auto/login.py` 的 `CODE_MAX_ATTEMPTS`），**不会重发码**；人随时**连续两次**回车放弃。

```
输入手机收到的短信验证码（连续两次回车放弃）: 12345          ← 手滑输错了
⚠️ 验证码没被接受：登录：提交验证码后没进入已登录态，但验证码输入框还在 —— 大概率是码输错或已过期
   还有 2 次机会：码没过期的话**重新输一次即可**（不会重发码，也不会重跑整条流程）。
输入手机收到的短信验证码｜第 2/3 次重输（连续两次回车放弃）: 123456   ← 这次对了
```

**为什么这么做**：验证码是人手输的，打错一位很常见。原来错一次整条用例就 fail，
想再试只能重跑 —— 而重跑会**重新发一次码**：短信撞服务端限流（见「坑 12」），
邮件要人再翻一次邮箱。`test_forgot_password_reset_manual` 本来就要连发 2 个码，
是最容易被自己反复重跑逼到限流的一条。

**只对「码错」重试，其它错立刻冒泡。** 区分口径是 `CodeRejected` 异常：

| 判定 | 含义 | 处理 |
| --- | --- | --- |
| `CodeRejected` | **页面还停在输入态**：短信 `CodeInput` 还在 / 微软 OTP 输入框还在 / 绑定弹窗还在 / 忘记密码页 `CodeInput` 还在 | 重问人（不重发码） |
| 其它 `LaunchError` | 控件找不到、按钮点不动、**大厅被遮挡** | 直接 fail，不重试 |

⚠️ **微软那条特殊：有窗口遮挡时不算码错。** WebView2 被遮挡就不渲染、登录页永远
提交不出去（「坑 15」那条超时 40s 的真因），而这时 OTP 输入框也还在 ——
判成码错会让人反复重输，可问题根本不在码上。所以 `wait_microsoft_logged_in`
只在「**无遮挡 + OTP 框还在**」时才抛 `CodeRejected`。

⚠️ **`CodeRejected` 继承 `LaunchError`**：没人接住时行为和改动前**完全一致**（用例 fail），
所以这次改动不会让任何一条老路径“变绿”。

**边界**：上限 3 次是刻意的 —— 连错多次可能触发服务端锁定。若码真过期/没收到，
连续两次回车放弃后重跑本条用例（那才会重新发码）。

守卫：`tests/unit/test_login_policy.py`（重试范围 / 上限 / 遮挡不判码错 / 放弃不提交 /
**单次空行只重问不放弃**）
+ `tests/unit/test_manual_loop_policy.py`（AST 检查：**重试里不许出现发码调用** ——
塞进去功能看着正常，只是每次重输都多发一条短信，静默地把测试号发到限流）。

#### 单次空行不再当「放弃」——发码即 skip 的坑（2026-10-27）

**现象**：节点跑人在环，短信验证码**发出去了**，用例却在 1.4 秒内 skip「人工放弃回填」，
人根本没机会输码。

**根因**：Windows 控制台输入缓冲**按控制台共享**。农场 agent 起 pytest 前先问了两轮
（是否参与 / 是否测改密码），人回「能」时**多敲的回车留在缓冲里**；pytest 继承同一个控制台，
它的第一处 `input()`（短信用例 `_ask_code`）把这条空行当成回答读走 → `ask_code_until_accepted`
判「放弃」→ skip。一条真短信就这么白发了。

**两道一起修**（缺一不可）：
- **agent 侧**：起 pytest 前 `FlushConsoleInputBuffer(STD_INPUT_HANDLE)` 清掉残留整行
  （`tools/farm_agent.py::_drain_console_input`，交互分支内、`subprocess.run` 之前）。
  守卫：`test_run_suite_drains_console_input_before_interactive_pytest`。
- **用例侧**：`ask_code_until_accepted` 把「一次空行 = 放弃」改成「**连续两次空行 = 放弃**」，
  第一次空行只重问、**不重发码** —— 兜住人在等待时误触回车那种情况。
  守卫：`test_login_policy.py` 的 `..._single_empty_reprompts_then_accepts_code`。

⚠️ **人在环那一段的输出不落 `logs/`**：提示语必须直接打到终端才能让人看见，
重定向进日志的话人只能干等、而日志里看着一切正常。用例结果仍在证据目录的
`summary.json` / `report.html` 里；回执里那条记录带 `interactive: true`，
汇总时能区分「无人值守跑的」和「真人守着收码跑的」。

⚠️ **`--local` 走的是 `run_suite`、不是 `execute_suite`，证据不回传农场** ——
只留在本机 `reports\evidence\<节点>\<时间戳>\` 下。要进农场汇总，改走
「投任意任务 + agent 问时答能」那条路。

#### 登录后「绑定手机号」弹窗（2026-09-22 新机实测）

在**没绑过手机号**的账号上，登录成功紧接着会弹一个绑定手机号的弹窗，挡在主界面前面。
处理动作全自动，人只管收码：

```
自动填号 → 自动点「获取验证码」→ 终端自动跳到最前 → 人输短信码 → 自动点确定
```

- **号码走 `HALL_BIND_PHONE`，没配就回退到 `HALL_TEST_USER`**
  （大多数情况下"要绑的号"就是"登录用的号"，所以新机不用额外配）。
  `bootstrap` 生成的 `farm_node.env` 模板里有这一项。**号码不落盘、不进 git。**
- **没弹就是没弹**（账号已绑过），那是正常情况、不是失败 —— 只在终端打一行字。
- **人回车 = 放弃绑定**：会自动把弹窗关掉。⚠️ 这个弹窗是**模态**的，
  留着不关，后面每条用例（点用户区、退出登录）都点不动。
  所以任何失败路径都会先关弹窗再抛错。
- **`logout()` 现在会自动收掉残留的绑定弹窗**（`dismiss_bind_dialog`，2026-09-22 补）。
  放在 `logout()` 这个共用处，是因为**只有人在环那两条会自己处理弹窗** ——
  无人值守的 `test_microsoft_login_sso` 登进去也可能弹，它走 finally 里的 `logout()`，
  弹窗挡着用户区 → 抛「退出登录：点不开用户菜单」，**看着像登出功能坏了**。
  `dismiss_bind_dialog` 默认**只探一次不等待**（`timeout_sec=0`），
  不会给每条登出用例加一个超时。
- 必须排在 `logout()` **之前** —— 这就是它被塞进登录用例、而不是单开一条的原因。
- ⚠️ **控件 aid 是按大厅既有弹窗的命名习惯推的，尚未在真机上探过壳**。
  找不到控件时会把**整进程的控件树**落到 `reports\bind_ui_dump\<时间戳>.txt`
  （含 control_type / aid / name / 矩形），报错里也会给路径 ——
  拿那棵树把 aid 补进 `hall_auto/login.py` 的 `_BIND_*_AIDS` 即可，
  **不用让一线重跑一次抓**。补完顺手把这段注释和 `探壳结论.md` 一起更新。

#### ⚠️ 微软【发送验证码】点完必须验（2026-09-22 新机踩出）

现象：脚本跳到微软登录界面后**没点【发送验证码】就回来问人要码**，人只能自己去点一下。

根因是原来那个实现**只点一下、不验证**：webview 里 `invoke()` / `click_input()`
都可能静默失败，于是"没点"和"点了"在代码里长得一模一样。
（同一形态还有：同名节点里先命中 `Text` 而不是外层 `Button` ——
`invoke()` 必失败、`click_input()` 又只认矩形，点了跟没点一样。）

现在：**同名节点里 `Button` 优先** → 点前 `_bring_to_front()` 确认窗口真在前台
（`click_input()` 依赖前台）→ **点完等代码输入框出现**（那是页面上唯一与"码已发出"
一一对应的可观测变化）→ 等不到就落盘控件树 + 抛错，
报错里带上"找到过几个同名节点"。

**所以以后再看到"没点发送验证码"，先看报错里那句"点了但代码框没出现"** ——
有它就是点没生效，没有它才是压根没找到按钮，两个方向完全相反。

守卫：`tests/unit/test_login_policy.py`（注入法验过能红）。

守卫：`tests/unit/test_farm_agent_policy.py` + `tests/unit/test_suite_planning.py`（注入法验过能红）。

**第 4 步为什么是「装」而不是「只检测」**（2026-09-18 改）：`hall_auto/security.py::extract_package`
用 `7z x` 解包待检安装包，而钉住包本来就在 `installer_dir/fixtures/7z2602-x64.exe`
（`tools/reset_fixture.py` 早就用它静默装了）。包在手边还让人去官网下一趟没道理。

**这一步做两件事，顺序有讲究**：①先确保钉住包在手 ②再按需装 7-Zip。
**①必须与"本机装没装 7-Zip"解耦** —— 那个包有两个身份（7-Zip 安装源 + P1-A 更新夹具起点），
早先只在"7-Zip 没装"时才去取它，于是**已经装了 7-Zip 的机器永远拿不到夹具包**，
`test_update_fixture_via_hall` 因"钉住安装包不存在"直接失败（2026-09-18 发现并修）。

- 装的是**钉住的 26.02，不是最新版** —— 它同时是 P1-A「更新夹具」的起点
  （大厅目录里的 7-Zip 比它新，更新列表里才永远有它可更新）。装最新版会让
  `test_update_fixture_via_hall` 的起点断言失配、用例转 skip。
- **非管理员不调安装器**：装到 `C:\Program Files` 要管理员，非提权直接调会弹 UAC 把脚本卡死。
- **拿不到包 / 装不上都不算铺设失败**（只影响 P2 解包和 P1-A 更新用例）——
  早先版本在环境自检里对缺 7-Zip 直接判 `fail`，会让一台机器明明能跑 launch/apps/login
  却整体报退出码 1，是假警报。第 9 步（安装包准备）对夹具包也同理：只记日志，不判失败。
- **Python / Git 不能自动化**（引导悖论：脚本本身是 Python 写的、代码本身是 Git 管的），
  这两样是唯一的"第 0 层"人工项。7-Zip 曾经也被当成人工项，现已消除。

**P2 安全验证的工具已可分发**（2026-09-18 改）：`security.tools_dir` 指向
`<installer_dir>/fixtures/security_tools`（CheckAppV / SignAppsV / SignCheck_v2.ps1 / signcheck_v2.zip）。
这些是内部工具**不进公开仓库**（红线），但**共享盘不是 git 仓库** ——
包源机的 `C:\hall-packages\fixtures\security_tools\` 放一份，第 8 步就会自动备到每台节点。
所以「N 台机器拷 N 次」压成了「1 台机器拷 1 次」，新机器上 `security` 不再必然 skip。

第 8 步的口径：**关键文件齐就一个字节都不拷**（幂等）；共享盘上没有 / 不可达 /
拷完仍缺关键文件 → **只提示不判失败**（只影响 P2，不该让整台机器的铺设判死）。

### 三档输出：`[OK]` / `[WARN]` / `[FAIL]`（2026-09-22 加）

**「不阻塞」和「没问题」是两件事 —— 别用 `[OK]` 表示前者。**

| 标记 | 含义 | 结果行 | 退出码 |
|---|---|---|---|
| `[OK]` | 真做成了 | — | 0 |
| `[WARN]` | **不阻塞，但必须让人看见**（如"配了共享盘却连不上"） | 单独列一遍 | 仍是 0 |
| `[FAIL]` | 真失败 | 计入 | 1 |

为什么加：2026-09-22 真机第 7 步两条共享**都**连接失败，却打了 `[OK]` ——
一线据此以为共享盘没问题，一直到取包/农场那几步才炸，排查方向全歪。
现在"配了却连不上"一律 `[WARN]`，报告 JSON 里也单列 `warned` 字段。
**`[FAIL]` 优先于 `[WARN]`**：一步既报警又失败时显示 `[FAIL]`。
它必须在第 7 步之后 —— 没认证过共享盘就取不到。

**`farm_root` 落盘（2026-09-18 改）**：第 5 步把 `HALL_FARM_ROOT` 的值写进
`config.local.yaml` 的 `farm_root`，`farm_agent` / `farm_control` 改为
**环境变量 > 配置 > 硬退出**。这样节点机**不必每次开新窗口重设环境变量** ——
以前忘了设的表现是"节点在跑但永远说无任务"，从表面完全看不出根因。
本次没设环境变量时**保留上一轮写进去的值**（重跑 bootstrap 不会擦掉配置）。

⚠️ **落盘的前提是"跑第 5 步的那一刻环境变量有值"，不是"跑过 bootstrap"**（2026-09-21 踩）：
两个条件不等价 —— 跑过 bootstrap 但当时没设 → 配置里**依然是空的**，那台机器每开一个新窗口都得重设。
**最容易被漏的是包源机/控制机自己**：它通常不参与"铺环境"，却要跑 `dispatch`/`status`，
报的错就是「未设 HALL_FARM_ROOT，config.local.yaml 里也没有 farm_root」。
补法：临时 `$env:HALL_FARM_ROOT=...`，或带变量重跑一次 bootstrap，或在 `config.local.yaml` 末尾加
`farm_root: \\LAPTOP-VS5F7HF4\hall-farm`（UNC 前面**两个反斜杠**）。自测：不设任何环境变量跑 `farm_control.py status`。

### 跑批 = 三个窗口同时活着

| 谁 | 干什么 | 什么时候能关 |
| --- | --- | --- |
| 控制机（包源机 `LAPTOP-VS5F7HF4`） | 开机、不休眠、共享常开 | 整批跑完 |
| 测试机 | `farm_agent.py --loop` 常驻 | 整批跑完 |
| 控制机 | `run_farm.py` 一条命令走完「投任务 → 等结果 → 出报告」 | 跑完自动退出 |

**缺任何一条，现象都一模一样**：任务躺在 `tasks\` 里没人取，控制机只看到「待执行 N 个」永远不动，
**而节点侧一点报错都没有** —— 所以这类问题在控制机上永远查不出来，必须回节点看 agent 窗口。

**用 `run_farm.py`，别分开敲 `dispatch` + `status`**：前者会在任务投出去 90 秒还没被取走时
**直接把排查清单打出来**；后者在这个状态下只显示「待执行 N 个」，一个字都不提示
（2026-09-23 用户就是被这一点耗住的）。退出码：`0` 全部交回执 ／ `1` 超时 ／ `2` 投任务就失败 ／ `130` Ctrl+C。

⚠️ 2026-09-23 踩过：清单步骤十六原来把 `--once` 和 `--loop` 并列成「**挑一条敲，别连着敲**」，
`--once` 还排在前面、标着「首验」；手册 3.2 更直接把它写成「**方式 A（推荐）**」。
**`--once` 的语义是「去看一眼，有任务就跑、没任务就退出」** —— 先敲它、后投任务 = 任务永远没人取。
现在清单步骤十六**只留 `--loop`**，`--once` 降级为「只想验链路、不能用来跑批」的说明。

### 看进度：`farm_control.py status` 三行数字怎么算

口径（`tools/farm_control.py` 的 `cmd_status`）：

| 那一行 | 数的是 | 文件形态 |
| --- | --- | --- |
| 待执行 | `tasks/*.json` | 控制机投出去了、**节点还没取** |
| 执行中 | `tasks/*.json.running` | 节点**取走时**才改名成 `.running`（防同一台机器重复取） |
| 已完成 | `done/*.json` | 节点跑完写的回执 |

**所以「刚投完」必然是「待执行 N 个、执行中 0 个、已完成 0 个」** —— `dispatch` 只写了
`tasks/<节点>.json`，一个字节都没碰 `.running` / `done/`。节点最多 `POLL_SECONDS`（30 秒）
之后才取走，状态才翻成「待执行 0 个、执行中 1 个」。**这段窗口不是故障。**

**判据：待执行数超过 30 秒还不降 = 节点侧的问题，不是控制机的问题。**
三种可能：① `farm_agent` 没在跑；② 在跑但连不到农场目录；③ **任务投给了别的节点**（见下）。
**前两种控制机这边看不出区别** —— 去节点那个窗口看有没有心跳行
（见《测试机操作手册》3.2 那张表；`--once` 下「农场不可达」还会返回退出码 3）。

#### ⚠️ 第三种：投错节点 —— 节点窗口显示「无任务」**是对的**，不是故障（2026-09-28）

**现象**：控制机「待执行 1 个」不降；节点窗口每 30 秒一行「无任务」、**心跳正常、没有任何报错**。

**根因（两层，第二层才是真的）**：

1. **机制**：`dispatch --nodes` 是**自由字符串**，`farm_control.py` **不校验节点名**。
   投给 `DESKTOP-DOHED68` 就写 `tasks/DESKTOP-DOHED68.json`；而节点 `LAPTOP-68TGB8VB`
   只轮询 `tasks/LAPTOP-68TGB8VB.json`（文件名 = **它自己的主机名**）。
   **两边各自都完全正常，只是对不上号。**
2. **为什么人会投错 —— 发放文档的锅，不是一线粗心**：两份发放文档
   （《新机操作清单》《测试机操作手册》）里**所有**投任务示例都写死
   `--nodes DESKTOP-DOHED68`（= **第一台**测试机的真名）。一线照着抄，必然投给旧机器。
   **2026-09-28 用户原话：「你这个新机操作清单上不应该是在哪台测试机上都能够适配的吗」**
   —— 对，就该适配。**这不是操作失误，是文档缺陷。**

**这一条会骗人**：按上面的判据你会去节点窗口找故障，而那个窗口显示的是「无任务」——
**看着像"节点连不上农场"，其实是"投错人了"**。而且节点这时对任何农场故障都毫无反应
（它压根没在等这个文件），越查越歪。

> **文档里"两边名字必须一致"的警告拦不住它**：被比较的两端（节点心跳示例 /
> 控制机 `--nodes` 示例）**是同一个写死的名字** —— 互相一致、却都不是眼前这台机器。
> **警告看着被满足了，其实一点用没有。** 凡是"示例里带具体值"的地方都有这个毛病。

**判据（一条命令，在控制机上）**：

```
.\.venv\Scripts\python.exe -X utf8 tools\farm_control.py status
#   →  待执行: DESKTOP-DOHED68.json      ← 看这里！节点名和正在等任务的那台机器对不上就是它
```

**修法**：按正确的节点名重投（旧的 `tasks/<错节点>.json` 不会自己消失，见下）：

```
.\.venv\Scripts\python.exe -X utf8 tools\farm_control.py dispatch --nodes LAPTOP-68TGB8VB --suites launch
```

**收尾**：投错的那份**会一直留在 `tasks/`**，于是 `status` 永远显示「待执行 1 个」——
**它会长期污染状态行，把真问题盖掉**。确认那台机器不跑这批，就删掉：

```
Remove-Item C:\hall-farm\tasks\DESKTOP-DOHED68.json
```

**防复发（2026-09-28 已做）**：

- 两份发放文档里的节点名**全部改成 `<节点名>` 占位符**，并写明
  「填**节点 agent 心跳里打出来的那个名字**」。尖括号还顺带保证**照抄会直接报 PowerShell
  语法错** —— 不会像写死的真名那样"悄悄地"投给别的机器。
- 新增守卫 `tests/unit/test_sync_handbook.py::test_release_docs_never_hardcode_a_test_machine_name`：
  **发放文档里只许出现常量机器**（共享盘宿主 `LAPTOP-VS5F7HF4`，每台机器都要连它），
  **任何具体测试机名一律报红**。负路径验过会红。
- `dispatch` 本身**加不了守卫** —— 投给一台真实存在、只是没开机的机器，语法完全合法。
  **这一层只能靠文档不出错 + `status` 把节点名打出来。**

⚠️ 2026-09-23 踩过：两份手册原来的示例写的是「待执行 0 个，执行中 2 个，已完成 3 个」+
`R01.json.running` / `R03_task_...`，`aggregate` 那段写「覆盖节点 5 台，用例 157 条」——
那是**5 台机器跑到中途**的快照，单机刚投完时**一个都对不上**，看着像投失败了。
已改成三态示例（刚投完 / 取走后 / 跑完）。**改这两处前先确认改的是"能对上的形态"，别再写多机快照。**

### 节点凭据通道（`farm_node.env`）

**为什么要有这个文件**：任务文件躺在**组内可读**的共享盘上，密码绝不能写进去；
但每台机器手工设环境变量既不现实也容易漏。所以拆成两个通道：

| 通道 | 内容 | 载体 | 敏感 |
| --- | --- | --- | --- |
| 任务环境 | `HALL_ALLOW_INSTALL` / `HALL_NODE_ID` / `HALL_FARM_ROOT` / `HALL_PACKAGE_*` / `HALL_INSTALLER_DIR` | 共享盘 `tasks/<node>.json` 的 `env` 字段 | 否（白名单校验） |
| 节点凭据 | `HALL_TEST_USER` / `HALL_TEST_PASSWORD` / `HALL_TEST_NEW_PASSWORD` / `HALL_MS_USER` / `HALL_SHARE_USER` / `HALL_SHARE_PASSWORD` | 各机本地 `farm_node.env`（**已 gitignore**） | **是** |

**优先级：进程环境变量 > 任务文件 env > 节点凭据文件。** 人工临时调试设的值不会被文件顶掉。

任务文件里出现敏感键或白名单外的键 → **直接拒绝并记入日志**，不静默丢弃。
`farm_agent` 的日志和回执里会带一行凭据状态（`密码凭据 / SSO 凭据 / 改密凭据`），
用于汇总时区分"真失败"和"没配凭据所以跳过"。

### 卸载/重置的两道闸（`tools/reset_machine.py`）

**血泪教训**：早期 `reset_before_run()` 是「先卸载、再去拿包」，且**不看任何门禁**。
办公机上误跑一次，大厅被卸掉而包又拿不到 → 机器直接废掉。

现在改成**只读预检在前、破坏动作在后**：

1. **预检（只读）**：四个来源（本地 / 缓存 / 共享盘 / 下载）能不能拿到包？拿不到 → **抛 `ResetBlocked`，不动现有安装**。
   - 下载分支**只认显式配置的 `download.url_template`**；默认那个 CDN 模板是猜的（问过组长两次，官方没有 URL，实测 404），
     所以空模板一律判"拿不到"，**不允许拿它当挡箭牌**。
2. **门禁**：`HALL_ALLOW_INSTALL=1` 或 `--allow-uninstall` 才允许真卸载。没开 → 只报告"检测到已装，跳过卸载"。
3. **备包**：预检通过后才真正把包备齐。**不再 `mkdir installer_dir`** —— 那会造出一个空目录骗过后续检查（假绿）。

`reset_machine.py` 被拒绝时 **退出码 3**，并写一份 `blocked` 报告，便于跑批脚本区分"被拦"和"真失败"。

**核心原则：先检测、缺什么才装什么。** 20 台机器环境不一样，
重跑 bootstrap **不该产生多余的安装动作，也不该碰网络**。

**第 2 步的依赖判定（`.venv/.deps_ok` 标记 + 实测双保险）**：

- 装成功后把 `requirements.txt` 的 SHA256 写进 `.venv/.deps_ok`
- 下次跑：先比哈希，一致再**实际 import 校验**一遍，两步都过才跳过 pip
- **为什么不能只信标记**：标记可能被手工删、venv 可能被清理、pip 可能半途失败。
  标记只用于"快速跳过"，**不能单独作为依据**（已单测锁住这条防线）
- `requirements.txt` 变更 → 哈希不匹配 → 自动重装

**第 7 步为什么不无脑重建**：`schtasks /Create /F` 会**重置触发时间**。
正在跑批时重建会把任务状态抹掉。所以先 `schtasks /Query /XML` 看任务在不在、
动作是否指向本仓库脚本，是就跳过。要强制重建：先 `schtasks /Delete /TN HallAutoP1 /F`。

**第 5、6 步失败不算铺设失败** —— 共享盘不可达或没凭据时只记录提示，不阻塞。
理由：某台机器可能有本地包，或后面会配下载地址，不该因为共享盘的问题把整台机器判死。

### 农场目录结构

```
farm_root/            （HALL_FARM_ROOT 指向）
  tasks/<node>.json   控制机投放的任务
  done/               节点跑完的摘要
  results/<node>/     节点回传的证据目录（整个 run 目录）
  logs/               节点执行日志
```

### 套件与并发预算（`hall_auto/suites.py`，改前先看这里）

| 套件 | 并发 | 理由 |
| --- | --- | --- |
| `unit` / `launch` / `apps-detect` / `settings` / `security` | **全并行** | 不碰服务端，不互相干扰 |
| `install` / `apps-lifecycle` / `login` / `wb` | **限流 ≤5 台** | 打更新服务、厂商 CDN、账号服务；不限流会被限流 → 假失败 |
| `wb-install` | **全局串行** | 522MB 厂商包走厂商 CDN，多台同时装互相限流拖死 |
| `login-manual` | **全局串行** | 人在环，永不进农场 |

`farm_control.py dispatch` 会打印实际生效的并发预算，别忽略那几行。

**⚠️ 规模前提（2026-09-18 组长确认）**：实际是**一批 5 台、跑完再换下一批**，
不是一次同时跑 20 台。所以：

- 上表的 `max_concurrent=5` **在 5 台规模下根本不会触发**，等于天然对齐，不用调
- **`max_concurrent` 做的是「逻辑分片」不是「物理节流」**：20 个节点都拿到任务，
  按 shard 错开。节点侧 `farm_agent.py` 拿到就开跑，**没有强制节流的机制**
- **批次调度（一批跑完才投下一批）目前没有实现**，暂时也不需要——
  5 台以内直接 `dispatch --nodes R01..R05` 就是一批的效果
- 触发补做的条件：真出现「20 台机器、需要无人值守连跑 4 批」时。
  做法是 `farm_control.py` 加 `--batch-size` + 轮询 `done/` 的循环，半天的事

### 分片

- `--shard-id` / `--shard-count`（`tests/conftest.py` 实现）：按收集顺序取模，**不重不漏**（实测 157 条切 2 片 = 79 + 78）。
- 为什么不用 `pytest-xdist`：它只做单机多进程、跨不了机器；且这套用例有全局机器状态（装/卸、注册表、前台窗口），同机多进程也会互踩。
- 全并行套件不分片（每台跑完整套件）；限流套件按 `max_concurrent` 分片。

### 结果汇总

**想看「某一次投批」整体跑得怎么样：`results/<节点>/按批/<日期_时刻>_<任务号>.html`**
（2026-10-28 起每次 `aggregate` 自动生成，一次投批一份、不跨批合并；页头带任务号 / 完成时间 /
代码 rev / 通过-失败-错误合计，表里每行链到该套件自己的 `report.html`）。
节点 `index.html` 顶部「按投批看」表一次投批一行、新在上，点任务号就进这一页。
补某一批：`aggregate --task <任务号>`（只写这一批的单批页，不碰总矩阵）。

`aggregate` 产出 `aggregate_report.html`：各节点统计 + **轮次表**（含**套件**列，轮次名可点进该轮报告）
+ 节点环境表 + **节点 × 用例矩阵**（✓ 通过 / ✗ 失败 / **! 错误** / – 跳过 / · 未跑到）。
矩阵是兼容性结论的正确形态 —— 能一眼看出「哪台机器挂在哪条用例」，而不是一堆汇总数字。
⚠️ 矩阵是**跨批合并**的（老批次的格子带 °）—— 它回答「现在各机什么状态」，不回答「这一次跑得怎么样」，
后者看上面的单批页。

#### 目录名对不上套件？看 `results/<节点>/index.html`

**症状**：`results/<节点>/` 下全是 `LAPTOP-x_2026-09-29_1349` / `..._1353` 这种
**只带节点和时间**的目录名。一个节点跑过 133 轮之后，在资源管理器里完全分不清谁是谁，
也就没法「拿报告去对应校验」。

**根因**：目录名由 `hall_auto/evidence.py` 的 `new_run_dir()` 生成，只拼「节点_时间」，
不含套件。**套件名一直躺在每轮的 `node_env.json` 里**（`farm_agent.py` 写的），只是没人把它摊到目录这一层。

**解法**：`aggregate`（或单独的 `index`）会在每个节点目录下写一份 `index.html`，
把「**run 目录名 ↔ 套件 ↔ 结果**」并排列出 —— 顺序与资源管理器一致，可按套件筛、可搜，
每一行都能点进该轮报告。**目录名本身不改**：那要所有节点 `git pull` 一次，收益不抵成本。

```powershell
# 只要索引、不要矩阵报告（快得多）
.\.venv\Scripts\python.exe -X utf8 tools\farm_control.py index
```

守卫：`tests/unit/test_farm_control_policy.py` 的「节点索引」段（含「目录名与套件必须在同一行」
和「老节点无 `node_env.json` 时退化成 module 名」两条）。

#### 归档副本（`汇总/aggregate_<时间戳>.html`）

根目录那份 `aggregate_report.html` 是**固定文件名、每跑一次覆盖一次** —— 10-09 那轮的汇总报告
就是这么没的，想跟 10-10 的结果做跨批次对比时无据可查。所以每次 `aggregate` 另存一份带时间戳的到
`汇总/`（同一秒连跑自动加序号）。**根目录那份保留**：手册/清单里承诺的路径就是它，挪走要同步三份文档。

**`! 错误` 与 `✗ 失败` 必须分开读**（2026-09-22 起单列）：

| 符号 | 含义 | 该看什么 |
| --- | --- | --- |
| ✗ 失败 | 用例**跑了**，断言挂了 | 断言原文 → 大概率产品缺陷 |
| **! 错误** | **setup 阶段就崩，用例一行都没执行** | 堆栈（临时目录被拒 / 夹具起不来 / 环境缺件）→ **不是产品结论** |
| – 跳过 | 缺前提（凭据/夹具/清单）自动 skip | skip 原文里的类别前缀，见「跑批结果怎么读」 |

⚠️ **矩阵是跨轮次合并的，别把老结果当最新结论。** 一个节点可能这轮跑 `launch`、下轮跑 `settings`，
所以同一节点不同用例可能来自不同 run。报告里：

- **鼠标悬停任意一格**可看它来自哪一轮（`来源轮次: <run>（完成时间）`）；
- 带 **°** 的格子 = **本节点最新一轮没跑到这条**，用的是更早轮次的结果；
- **轮次表**列出该节点跑过的每一轮及其通过/失败/错误/跳过，`← 最新` 标出最新一轮。

**为什么专门做这套标注**：`aggregate` 按 `nodeid` 合并各轮、**后面的覆盖前面的**，但"覆盖"只在
**新那轮有记录**时才发生 —— 新那轮没跑到（没投这个套件，或那条用例 setup 就崩了）时，
**老记录会留在矩阵里冒充最新结果**。2026-09-22 实锤过：节点上 188 条用例因
`%TEMP%\pytest-of-admin` 拒绝访问而在 setup 就崩，当时 conftest 不记 ERROR，
于是 `summary.json` 写 `total 273 / passed 273 / failed 0`，矩阵里那一片挂着上一轮的 ✓ ——
**整行看着全绿**（假绿）。现在 ERROR 记成 `error` 并单列，报告里也标了来源轮次，两个口子都堵上。

## 环境与依赖（多机）

- **显示缩放不影响正确性，不要设为 100%。** 脚本经 `hall_auto/screen.py` 在 import 时设
  Per-Monitor Aware（`SetProcessDpiAwarenessContext(-4)`），全套走**物理像素**坐标，
  与 UIA `rectangle()` 同一套。本机真实缩放 **150%**（物理 2560x1600，DPI 144），
  P0/P1/P2 全部套件在此前提下实测跑通，按钮面积判据（360x60）就是在物理像素下标定的。
- **读 DPI / 屏幕尺寸前必须先设 DPI 感知**，否则读到被系统缩放虚拟化后的假值：
  实测同一台机器，DPI-unaware 进程读出来是 `96 DPI / 1707x1067`（假），
  设 Per-Monitor Aware 后才是真实的 `144 DPI / 2560x1600`。不设就检测会永远报「100%」。
  `hall_auto/dpi.py` 所有读数函数内部已自带这一步（`ensure_dpi_aware()`）。
- **真正的跑批门禁只有会话状态**：锁屏 / 息屏 / RDP 断开后会话变非交互态，
  抓屏拿黑屏、点击无落点 → 全套用例批量失败。`tests/conftest.py` 的 `_env_precheck`
  在非交互态直接 `pytest.exit(rc=3)`；调试可加 `--skip-env-check` 绕过。
- **节点标识**：`HALL_NODE_ID` 环境变量 > `config.local.yaml` 的 `node_id` > 主机名。
  证据目录形如 `reports\evidence\<node>_<日期_时间>\`，多机回传不撞名；
  报告页头显示节点/系统/缩放/分辨率/Python，多机结论可按维度分组。
- **新机铺设的两道预检（2026-09-21 补）** —— 这两样新机上常缺，但原来没人检查：
  - **磁盘空间**：第 1 步报 `installer_dir` 所在卷的剩余空间，低于 `MIN_FREE_GB`（3 GB）明确警告。
    盘满会在取包 / 装大厅时**拷到一半失败，报错长得像"共享盘坏了"**，一线会往完全错的方向查。
  - **pip 源可达性**：第 2 步装依赖**之前**先探一次（`_pip_net_ok` / `_pip_probe_target`，
    顺序 `PIP_INDEX_URL` > 代理 `HTTPS_PROXY` 等 > `pypi.org:443`），
    探不到就**几秒内**提示并给出两条绕法：① `pip config set global.index-url <内网镜像>`；
    ② 从已铺好的机器拷 `.venv` 过来 + `--skip-venv` 重跑（完全不碰网络）。
    不探的话 pip 自己会重试好几轮（几分钟）再抛一段截断的 stderr，一线分不清"没网"还是"包名写错"。
    **探测失败不拦路**（仍会尝试装）：探测有偏差，硬拦会把本来能装的机器判死，比不探更糟。
    **必须认代理** —— 裸 socket 不走 `HTTPS_PROXY`，不认代理就会给出假阴性。
  - ⚠️ **已铺好的机器重跑 bootstrap 连探测都不该探**（脚本承诺"重跑不碰网络"），有回归锁守着。
  - 除 **Python 3.12 64 位**（要在 PATH 里；**版本钉死 3.12** —— 离线 `wheelhouse` 是 `cp312` 的，
    装了 3.13/3.14 的无外网机器会在第 2 步 FAIL）和 **Git** 两样"第 0 层"项（引导悖论，只能人工）之外，
    其余前置条件都由 bootstrap 负责检查或安装。
- 机器台账模板 `machines.yaml`（人工维护）。

### 机器画像里的兼容性字段（`hall_auto/profile.py`）

**存在的理由**：多机跑批最大的价值是「找出只在某些机器上挂的缺陷」。但如果一台机器本身
缺 WebView2、或没登微软账号，跑出来的失败**不是产品缺陷**，是环境差异。
把这些字段采出来，汇总表才能按维度分组、区分「产品缺陷」和「环境缺件」。

`compat_facts()` 采集（**唯一的权威实现**，`tools/collect_machine.py` 和 `hall_auto/dpi.py`
的 `machine_profile()` 都调它，不再各写一份）：

| 字段 | 口径 |
| --- | --- |
| `webview2` / `webview2_version` | 读注册表产品码 `{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}`（HKLM 为主，HKCU 兜底） |
| `hall_installed` / `hall_version` | 大厅是否已装 + 版本 |
| `ms_session` | `yes` / `no` / `unknown` —— 数 `OneAuth` / `IdentityCache` / `TokenBroker` 下的条目数，**绝不读取 token 内容** |
| `ocr_zh` | OCR 是否具备中文识别能力 |

采集失败一律降级为 `unknown`，**不让画像采集把整轮跑批打断**。
`aggregate_report.html` 的节点环境表列：`os / screen / scale_percent / webview2 /
webview2_version / ms_session`，加上三个凭据列 `密码凭据 / SSO 凭据 / 共享盘`。

### 节点侧的四道防呆（`tools/farm_agent.py`）

跑批一次投几十个任务，节点侧任何一个静默错误都会污染整批结果：

1. **重复 task_id 拒绝** —— `dispatch` 重复投同一 `task_id` 时，节点看到
   `done/<node>_<task_id>.json` 已存在就直接拒，不重跑。避免同一任务跑两遍覆盖证据。
2. **空套件拒绝、且不写回执** —— 任务里套件列表为空时**绝不生成成功回执**。
   假绿比红灯危害大得多：一个空任务如果写了 `exit_code: 0`，汇总时会被当成"通过"。
3. **清理陈旧的 `.running` 占位文件**（`_reap_stale_running`）——
   上次进程被强杀会留下 `tasks/<node>.json.running`，导致后来所有任务
   `rename` 静默失败、节点一直报「无任务」，而任务文件明明躺在 `tasks/` 里。
   现在启动时先扫掉残留占位，并在异常时明确报错而不是静默 `return None`。
4. **空闲轮询必须留痕 + 农场不可达不许报"无任务"**（2026-09-21 加，见下）。

拒绝时**同时清掉自己建的 `.running` 占位**（两条拒绝路径都要），否则会把自己锁死。

**退出码约定**：`0` 正常／`2` 任务被拒收（`--once`）／`3` 农场不可达（`--once`）。

回执里带 `credentials` 字段（`密码凭据 / SSO 凭据 / 改密凭据`），用于区分
「真失败」和「没配凭据所以跳过」。

#### 第 4 道：`--loop` 空闲为什么要打心跳（2026-09-21 修）

**症状**：新机上跑 `farm_agent.py --loop`，打印两行之后**五分钟一个字都不出**，
现场判定"卡住不动了"。实际它只是在正常空转。

**原因**：空闲分支原来一个字都不打 —— 30 秒一次静默轮询。更糟的是它和**真故障长得一样**：

- UNC 一断，`Path.is_file()` 会把 `OSError` **吞成 `False`**，`take_task` 一路走到"无任务"；
- 于是节点在报平安，而它其实**一个任务都取不到**；
- 「真的没任务」和「共享盘断了」在屏幕上完全无法区分。

**现在**：

- 每次空闲轮询打一行心跳：`[17:12:07] 轮询 #1：无任务，30 秒后再查（等 ...\tasks\<节点>.json）`
  —— 带上**它在等哪个文件**，节点名和 `dispatch --nodes` 对不上时一眼就能核对；
- 启动时也打一行 `等待任务文件 <路径>`（同上的核对用途）；
- 农场探不到（`prepare_farm` 里 `mkdir` / `stat` 抛 `OSError`）时，心跳换成一段中文排查指引
  （包源机关了？`net use` 通不通？共享名写错？），**并且 `--once` 返回 3 而不是 0**；
- 所有关键 `print` 带 `flush=True` —— `--loop` 输出重定向到文件时是块缓冲的，
  不 flush 就攒在缓冲区里，又变回"看起来卡住"。

⚠️ **`--once` 打「无任务，退出」+ 返回 0 是"链路通了"的证明**，所以农场不可达时**不能**走这条路
（那是假绿：一线会以为只是没人投任务，实际包源机可能已经关了）。同理，
`mkdir` 失败以前会吐一段 Python traceback（`PermissionError: [WinError 5] 拒绝访问`）——
**看着像权限问题，实际多半是包源机关了**，现在统一变成那句中文指引。

回归锁在 `tests/unit/test_farm_agent_policy.py`（8 条：心跳不许空、要打等待文件名、
不可达要吼、`prepare_farm` 不抛、`--loop` 空转 3 轮必有 3 行心跳、`--once` 不可达返回 3 等）。


## 安装包获取与跑批前复位（2026-09-18 落地）

### 包从哪来（`hall_auto/fetch.py`）

查找顺序，**前三步都不碰外网就不碰**：

1. `installer_dir/<文件名>` —— 本地夹具目录（既有的老路，行为不变）
2. `installer_dir/_cache/<文件名>` —— 本地缓存（下过/拷过就不再取）
3. **共享盘**（配了 `package_share.dirs` 才走）—— 拷进本地缓存，局域网快且版本可控
4. 下载到 `_cache/` —— 组长 2026-09-18 要求「脚本在测试机自动下载对应大厅」

**3 不可达会被静默跳过、自动降级到 4**，绝不因为共享盘挂了让整轮跑批失败。

下载细节：

- **走 `.part` 再原子改名**（同盘 `os.replace`），并发时别的进程永远看不到半截包
- **配了 sha256 就校验**（`config.yaml` 的 `download.sha256` 映射，或 `update_fixture.sha256`）；
  没配只记录实际值。校验不过直接报错，绝不用坏包装
- 失败重试 3 次，间隔 2/4/8s 递增
- 只下 `zh-CN` 语言的包（`Accept-Language`），下错语言会让「关于页版本」断言全失配
- `HALL_ALLOW_PACKAGE_DOWNLOAD=0` 可全局禁掉下载（离线验收用）

共享盘细节：

- **探测必须带超时**（默认 5s，`fetch.SHARE_PROBE_SEC`）。UNC 路径 `is_dir()` 在断网时
  可能卡 20s+，逐个包都卡一次会让跑批变得极慢。超时即判不可达，走下载兜底
- **UNC 的异常类型和本地不一样**：网络断/凭据错抛 `OSError`（WinError 53/64/1326/1231），
  不是 `FileNotFoundError`。判断存在性必须 catch `OSError`，否则一条断网就崩
- 支持配多个共享盘（`dirs` 列表）做冗余，按顺序试，第一个不通用第二个
- `HALL_PACKAGE_SHARE` 环境变量可临时覆盖配置（单机切换用，不必改配置）

配置（`config.yaml`）：

```yaml
download:
  url_template: ""     # 支持 {filename} 占位；**空 = 禁止下载**（不再回落到猜的 CDN 地址）
  sha256:              # 文件名 -> 期望摘要，填了才校验
    myappstore_1.6.8.17S_Setup.exe: "<64位十六进制>"

package_share:
  dirs:
    - "//LAPTOP-VS5F7HF4/hall-packages"
    - "//LAPTOP-VS5F7HF4/hall-packages"   # IP 会变，机器名更稳
```

**⚠️ `url_template` 为空时 `fetch.py` 的下载分支不可用（2026-09-18 修正）**：
早期代码在模板为空时会回落到一个默认 CDN 模板（`dlcdnets.asus.com`）。那是**猜的**
——问过组长两次，官方没有稳定下载地址，实测这些 URL 404。
更糟的是它会让复位预检误判「包拿得到」，从而**放行一次注定失败的卸载**。
现在 `check_packages_available()` 只认**显式配置**的模板，空模板一律判"拿不到"。

**当前状态（2026-09-18 18:30 更新）：`download.url_template` 仍为空（组长没给地址）；
`package_share.dirs` 已填 `//LAPTOP-VS5F7HF4/hall-packages`（**机器名，不是 IP**）并端到端验证通过。**

⚠️ **必须写机器名**：2026-09-18 实测踩过 —— 原来配的是 `//192.168.0.4/...`，
本机重启后 DHCP 把 IP 换成 `192.168.0.8`，所有节点立刻报
「**系统错误 67 找不到网络名**」。报错看着像"共享没建"，实际是 IP 过期。

### 跑批前复位（`tools/reset_machine.py`）

组长要求「不论装没装对应大厅，都先检测，有检测到就先删掉，重新下载」。这就是它的可执行版本：

```
①（只读）预检包能否拿到 ── 拿不到 → ResetBlocked，退出码 3，现有安装原封不动
②（读门禁）已装大厅？门禁没开 → 只报告「跳过卸载」
③ 停止进程 + 静默卸载 + 等卸载完成
④ 备齐配置声明的安装包（不再 mkdir installer_dir）
```

**顺序不能反。** 早期版本是「先卸载、再取包」且无门禁 —— 办公机上误跑一次会把大厅卸掉而包又拿不到，
机器直接废掉。详细说明见上文「卸载/重置的两道闸」。

```powershell
.\.venv\Scripts\python.exe -X utf8 tools\reset_machine.py --dry-run   # 只报告不动手
.\.venv\Scripts\python.exe -X utf8 tools\reset_machine.py --allow-uninstall   # 真卸载（P0 层要管理员）
.\.venv\Scripts\python.exe -X utf8 tools\reset_machine.py --no-download       # 离线：只用本地/缓存/共享盘
```

`--allow-uninstall` 也可以由 `HALL_ALLOW_INSTALL=1` 替代（跑批链路上常用后者）。
**办公机永远别开这个开关。** 退出码：`0` 正常 / `3` 被闸拦下（拿不到包或门禁未开）/ 其他为真失败。

报告落 `reports/reset/reset_<node>_<时间>.json`。单个包拿不到记进 `packages[].error`，
但**预检阶段就整体拿不到时不会进入卸载步骤**。`--no-download` 且本地无包时报告 `ok: False`
并带 `installer_dir_exists`，不会造假绿。

### 屏幕常亮（两层，缺一不可）

组长 2026-09-18 确认测试机无人碰屏，靠脚本自己保证不睡。**分两层，管的不是同一段时间**：

| 层 | 实现 | 生效范围 | 管的空档 |
| --- | --- | --- | --- |
| 进程级 | `hall_auto/awake.py`（`SetThreadExecutionState`） | 只在该 python 进程活着时 | pytest 跑批期间 |
| 机器级 | `tools/set_keep_awake.ps1`（改当前电源方案超时值，可回滚） | 持久，重启不丢 | 跑批前 / 两轮任务之间 / 跑批后 |

**为什么两层都要**：进程级随进程退出自动失效，管不了「节点 agent 空转等任务」那几小时 ——
机器按 Windows 默认电源方案（显示器 10 分钟关、睡眠 30 分钟）**自己睡过去，连 agent 的轮询线程
一起停摆**，控制机看不到回执。现场表现是「投了任务没反应」，与「共享盘断了」「agent 崩了」
完全同形，排查方向从一开始就是错的。所以无人值守的节点机必须靠机器级那层兜住。

#### 进程级（`hall_auto/awake.py`）

- 用 `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED | ES_DISPLAY_REQUIRED)`
- **进程级、退出自动失效**，不改系统设置、不需要管理员
- **已接进 `tests/conftest.py` 的 `_env_precheck`（session autouse）**：只要跑 pytest 就自动生效，
  不用额外加参数。`--skip-env-check` 时也会跳过常亮设置
- `tools/farm_agent.py` 的 `main()` 一进来也持有它 —— 它是节点上唯一长期活着的进程
- 独立用法：`with keep_awake(): ...` 或 `keep_awake_for_process()`

**为什么不在 `with` 退出时还原**：session fixture 的 teardown 到进程真正退出之间可能很长
（P0 装/卸套件尤其明显），中途还原 → 屏幕可能就睡了，后面的用例全黑屏。
所以还原挪到 `atexit`，**整个进程生命周期内都保持常亮**。

**后台守护线程**：`keep_awake_for_process()` 起一个 daemon 线程（`_REFRESH_SEC=5` 秒一次，
幂等，重复调用不会起第二个），持续重设常亮状态；同时检测会话是否变成非交互态
（RDP 断开 / 锁屏），一旦变了就 `mark_session_lost()` 记下**第一次**发生的时间戳。

**RDP 断开只能检测、不能阻止** —— 这是 Windows 的硬限制，脚本改不了会话状态。
所以策略是**尽快失败而不是假装成功**：`conftest.py` 的 `_session_guard` autouse fixture
在每个用例后检查 `session_lost()`，命中就 `pytest.exit(returncode=3)`，
把整轮标成「会话丢失」而不是产出一堆假失败。teardown 时会打印丢失时刻与详情。

**「进程级这层不改电源计划」≠「机器级也不该改」**：机器级是全局持久设置，
跑批期间用它反而不可靠（别人/组策略把它改回去就失效，脚本被强杀还会留下烂摊子）——
所以**跑批期间**靠跟 pytest 进程同生共死的进程级那层。但没人跑 pytest 的那三段空档
必须由机器级补，它带改前备份 + 改后复核 + `-Restore`，不是裸 `powercfg /change`。
两层互不替代。

#### 机器级（`tools/set_keep_awake.ps1`）

改的是**当前电源方案**：显示器/睡眠/休眠超时 AC+DC 全设 0（永不）、合盖不操作、关掉屏保，
并把唤醒时的重新登录要求也关掉。**bootstrap 第 13 步**自动跑，幂等（先 `-Check` 只读，
已是常亮就一个设置都不改）。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\set_keep_awake.ps1 -Check    # 只读，rc 0=已常亮 1=会睡 3=读不到
powershell -NoProfile -ExecutionPolicy Bypass -File tools\set_keep_awake.ps1           # 设置（需管理员才改得动合盖项）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\set_keep_awake.ps1 -Restore   # 按备份还原
```

- **可回滚**：原值备份在 `%LOCALAPPDATA%\hall-keep-awake\power_backup.json`（**本机专属、不进仓库**）。
  **只在第一次跑时写** —— 第二次跑时值已经是 0，再写一份就把原值盖没了。
  **这个文件别删**，删了就只能手工把电源方案调回默认（没人记得住原值）。
- **改完必须回读复核**：只看 `powercfg` 退出码会假绿（组策略/第三方电源软件能把值顶回去）。
- **不碰组策略下发的屏保/电源策略**：只检测并提示，改策略是 IT 的事。
- ⚠️ **踩过的坑（2026-09-21 实跑抓出）**：`powercfg /query` 在「当前 AC/DC 索引」**之前**
  先打一段取值范围（`最小可能的设置: 0x00000000` / `最大可能的设置: 0xffffffff` / 增量），
  同样是 8 位十六进制。**按顺序取前两个**会把任何机器都读成「AC=0（永不）」
  → `-Check` 恒报 `[OK] 已常亮`、bootstrap 第 13 步一个设置都不改（假绿）。
  正确做法是取**末尾两个**（枚举型设置如合盖动作没有取值范围段，末尾两个同样是 AC/DC）。
  回归锁在 `tests/unit/test_keep_awake_machine_policy.py`，样本别删。

### 自建共享盘分发安装包（2026-09-18 实测通过）

**用途**：20 台测试机没有共享盘、也没有官方下载地址时，拿一台常开的机器当安装包源。

**⚠️ 先看这个判断**：这条路**技术上可行但运维负担重**（源机器必须常开、IP 会变、Wi-Fi 带宽争抢）。
优先顺序永远是：**① 公司现成共享盘 → ② 官方下载地址 → ③ 自建共享盘 → ④ U 盘手工拷**。

**本机实测记录（2026-09-18）**：在 `LAPTOP-VS5F7HF4`（Wi-Fi + 公用网络）
建共享，从另一台机器成功访问。踩过的坑见下，**按顺序做能少走弯路**。

#### 建共享：用脚本（推荐，幂等）

**`tools/provision_share.ps1`（2026-09-18 新增）** 把下面所有手工步骤一次性做完：
建账号 → 建两个共享 → 配权限 → 加防火墙 → 建农场目录 → 网络路径自测。

```powershell
# 管理员 PowerShell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\provision_share.ps1
# 已建过账号时可带密码，让脚本自检能真连一次：
powershell -NoProfile -ExecutionPolicy Bypass -File tools\provision_share.ps1 -SharePassword "<密码>"
```

开关：`-SkipPackages` / `-SkipFirewall` / `-SkipVerify`。
退出码：`0` 成功 / `2` 非提权 / `1` 有失败项。末尾会打印 `RESULT: OK|NO_SHARE_ACCOUNT|EXCEPTION` 便于日志抓取。

**两个共享的权限不一样，这不是笔误**：

| 共享 | 节点权限 | 为什么 |
| --- | --- | --- |
| `hall-packages` | **Read** | 只读包，节点只拷不写 |
| `hall-farm` | **Change** | 控制通道。节点要 rename 走 `tasks/`、写 `done/`、推 `results/` 与 `logs/`，给 Read 会让每个节点**静默失败** |

**为什么这步必须人工按一次提权**：建 SMB 共享是内核级特权操作，非提权进程报「系统错误 5 拒绝访问」，
且 UAC 的同意框画在安全桌面上，非提权进程碰不到。这是唯一绕不过的硬墙。
**但只需按这一次**——脚本幂等，5 台机器共用同一个共享，不需要每台机器提权一次。

脚本内有一条**防假绿**的设计：`Report()` 用 `$script:ok = $false` 而非裸 `$ok = $false`。
原因：PowerShell 函数内对未声明变量赋值会创建**函数局部副本**并静默丢弃，
结果就是脚本永远报 OK、永远退出 0。这类「假绿」比红灯危害大得多。

#### ⚠️ 坑 1：空密码账号无法网络登录（**这是最大的坑**）

Windows 默认策略**禁止用空密码账号做网络登录**。本机 `admin` 账号没设密码，
因此另一台机器用 `admin` 访问一律失败。

**解法：建一个专用的带密码共享账号**（别动日常账号的密码）

```powershell
Grant-SmbShareAccess -Name "hall-packages" -AccountName "hallshare" -AccessRight Read -Force
```


（报「密码不满足密码策略要求」）。**实际口令只走 `HALL_SHARE_PASSWORD` / `farm_node.env`，
不写进本文档**（项目红线：密码不进 git）。

> ⚠️ **2026-09-22 实测提醒**：现行口令是 **6 位纯数字**，与上面这条默认策略不符。
> 发新机建号前先在共享方跑 `net accounts` 看 `Minimum password length` ——
> 要么本机策略已被放宽，要么 `net user ... /add` 会直接报「密码不满足密码策略要求」。
> 这条以前是写死的字面值，误导过一轮；现在只留规则，不留值。

#### ⚠️ 坑 5：共享盘拷包会撞上 Windows 瞬时文件锁（2026-09-21 定位）

**现象**：偶发 `FetchError: 从共享盘拷贝失败 ...：[Errno 13] Access is denied: '...\_cache\a.exe'`。
**看起来**像权限问题，**实际**是别的进程短暂持有句柄：杀软实时保护会在文件 close 之后扫一遍
（索引服务同理），此时 `os.replace(part, dest)` 报 WinError 5/32。等几十毫秒就过去了。

**为什么当时查不出来**：它偶发（一次全量跑里出现 1 次），且**下载路径撞上同一种错误会自愈**——
`_download` 对 OSError 有 3 次重试，而 `_copy_from_share` 一次都不重试。两条路径对同一种
瞬时错误行为不一致，所以只有共享盘那条会硬失败。

**已修**：抽出 `_atomic_replace()`（瞬时锁退避重试，只重试 WinError 5/32/33/1224，
永久错误立刻抛），共享盘拷贝与下载改名都走它；共享盘拷贝另加 3 次整体重试。
回归锁在 `tests/unit/test_fetch_policy.py`（6 条）。

**排查提示**：遇到「拒绝访问」先分清是**永久**（ACL 真不对，重试也不会好）还是**瞬时**
（重试就好）。判据就是 winerror 码，别看到 `Access is denied` 就去改权限。

#### ⚠️ 坑 6：`[Errno 22] Invalid argument` —— 杀软把**刚写完的文件**判毒（2026-09-21 定位到根因）

**现象**：`tests/unit` 里有 4 条间歇失败，都报 `[Errno 22] Invalid argument`：

```
test_fetch_policy.py::test_ensure_from_share_copies_and_verifies
test_fetch_policy.py::test_share_copy_survives_transient_lock
test_fetch_policy.py::test_share_copy_fails_loudly_when_lock_persists
test_bootstrap_policy.py::test_seven_zip_fixture_comes_from_share_when_offline
```

**失败点是 `src.open("rb")`** —— 纯标准库，读的是**本进程刚 `write_bytes` 写出来的**文件。
栈长这样：

```
File "hall_auto\fetch.py", line 231, in _copy_from_share
    with src.open("rb") as fh_in, part.open("wb") as fh_out:
OSError: [Errno 22] Invalid argument: '...\Temp\pytest-of-admin\pytest-NNN\...\a.exe'
```

**注意报错里的文件名是 `src`**（源文件），不是 `.part` —— 很容易误以为"共享盘那个文件坏了"。
实际它是个本地临时文件，刚由测试自己写出来。

##### 为什么这 4 条以前"看不见"（2026-09-21 做发放版时顺带撞上）

`test_fetch_policy.py` / `test_bootstrap_policy.py` 这 13 个文件**没有 `unit` 标记**，
而运行手册写的标准单测命令是 `pytest tests/unit -m unit` —— 于是它们被**静默 deselect**，
屏幕上是「127 passed」一片绿。实际 `pytest tests/unit` 收 **434** 条，红的正是上面那 4 条。

**"绿"和"跑过"是两回事。** 已修：13 个文件补上 `pytestmark = pytest.mark.unit`
（`-m unit` 的选择集 127 → 434），并加了守卫用例
`test_repo_hygiene.py::test_every_unit_file_is_selected_by_the_unit_marker` 盯着别再漏。
**补完之后这 4 条就是红的** —— 根因是杀软，见下。

##### 根因（2026-09-21 探针实测，不再是猜测）

用 `ctypes` 直接调 `CreateFileW` 拿**真实 Win32 错误码**，一次就露了：

```
python open FAIL errno=22 winerror=None
CreateFileW 失败 GetLastError=225        <- ERROR_VIRUS_INFECTED
```

再查 Defender 自己的记录，拦的就是探针刚写的那几个文件：

```
Get-MpThreatDetection -> ThreatID 2147731250
   file:_C:\Users\admin\AppData\Local\Temp\av-w__mq8r8\payload
   file:_C:\Users\admin\AppData\Local\Temp\av-9rci_2xa\payload.txt
Get-MpThreat -> 2147731250 = Trojan:Win32/Bearfoos.A!ml   SeverityID=5
```

**完整链路**：Windows Defender 实时保护（`RealTimeProtectionEnabled=True`、
`BehaviorMonitorEnabled=True`）用 ML 模型（`!ml`）把进程**刚写出的**小文件判成
`Trojan:Win32/Bearfoos.A!ml` → 此后**任何**读它都返回 `ERROR_VIRUS_INFECTED(225)`
（Python 的 errno 表里没有 225，于是显示成 `[Errno 22] Invalid argument`）
→ **约 14 秒后文件被隔离删除**（再探就变成 `GetLastError=2` 文件不存在）。

**为什么像"某个进程一旦中了就一直中"**：判定是**按文件**做的（那个文件被标记了），
而 pytest 一个用例一个临时目录；同一进程里换读别的**新建**文件也一样中，
换成 3 秒前写的老文件、或 `C:\Windows\System32` 里的现成文件就正常。
跟目录、扩展名、文件内容都无关（`from-share` 这种纯文本照样中招）——
所以早先那几轮"换目录/换扩展名/关沙箱"的对照全都对不上号。

**本机同款证据**：DESKTOP-DOHED68（首台真机）红的那 2 条、
以及本机 `tests/unit` 全量跑的这 4 条，签名完全一致。

**反向确认（2026-09-21 首台真机实测）**：把杀软的实时保护**关掉**之后，同一批用例立刻转绿 ——
链路就此闭合（**关掉就好 = 与代码、与共享盘都无关**）。
但**别把"关杀软"当解法**，理由见下面「影响与应对」第一条。

**这条直接改掉应对顺序**：

1. **先跑探针**（10 秒，见下）。干净就直接跑，别动任何安全设置 —— 这是常态。
2. 探针报 225 → **先更新病毒库再复探**（管理员 PowerShell `Update-MpSignature`，
   或安全中心点「检查更新」）。误报是**库**的问题，换库比关防护便宜得多，也不削弱机器。
3. 更新完仍报 225 → 才轮到关实时保护 / 加排除项（下面两条路）。

⚠️ **别再拿「昨天关杀软就好了」当证据**。关掉当然"能通"，但代价一条不少（不持久、
削弱防护、管不了第三方杀软），而且它把一个**会自愈**的问题当成了解法 ——
下次真遇到，先试更新病毒库。

##### 影响与应对

- **不是仓库 bug**：`hall_auto/fetch.py` 里那行就是 stdlib 的 `open()`，
  读的对象是测试自己刚写的文件。别去改 `_atomic_replace`（那是坑 5）。
- **别加重试兜**：同一个文件连试 40 次、跨 20 秒全失败，它不是瞬时状态。
  （**唯一例外**见下面"自检重跑一次"——那是"换个进程重跑"，不是"同一进程原地重试"。）
- bootstrap 第 12 步（`tests/unit`）会因此报 FAIL，而失败项与代码质量无关。
  **现在第 12 步会自己换进程重跑一遍失败的那几条**：重跑转绿就判为环境级 flake、
  本步按通过计，并把首跑红的名单留在 `reports/bootstrap/selftest_*.log` 里；
  重跑仍红才判 FAIL，并且**点名提示"这是杀软误杀，别去改 fetch"**。
  **所以第 12 步红了、重跑又绿 = 环境层，不是代码坏了。**
- ⚠️ **重跑救不了"稳定拦"的机器**：杀软是按**文件**判的，而判定与读操作之间有竞态 ——
  本机（`LAPTOP-VS5F7HF4`）2026-09-21 实测就是**稳定拦**（4 条全红、换进程重跑仍全红），
  那时第 12 步就是真 FAIL，只能加排除项（见下）或换机器跑。
  首台真机 DESKTOP-DOHED68 只红了 2 条（4 条里的一半），属"竞态型"，重跑大概率能过。
- ⚠️ **"把杀软关掉就好了" —— 能通，但不是解法，别停在这一步**（2026-09-21 真机就是这样解开的）：
  - **不持久**：Defender 的篡改保护（Tamper Protection）、安全中心或组策略会把实时保护
    **自动开回来**（重启后尤其常见）。届时 bootstrap 又红，而现场的人只会以为"代码又坏了"。
  - **它挡的不只是自检**：真正要紧的是**从共享盘取包进 `_cache`** 那一步 —— 同样会被拦，
    而它失败会直接卡住 P0/P1。所以排除项要按「让取包能过」来配，不是「让第 12 步变绿」。
  - **第三方杀软不在本脚本管辖内**：`add_av_exclusions.ps1` 只调 `Add-MpPreference`（**Defender 专用**）。
    若这台机器上真正拦的是 McAfee / 360 / 火绒之类，得去**它自己的控制台**加，脚本改不了它。
    → 先确认"关的是哪一个"，再决定用哪条路。
- ✅ **现阶段怎么做（2026-09-22 用户定调 + 当天复测修正）**：《新机操作清单》步骤八（杀软探针）是一线自助入口，
  但**第一步是跑探针，不是关杀软** —— 探针干净就别动安全设置（复测后这是常态）；
  报 225 先更新病毒库再复探；仍报 225 才关实时保护。清单里三种情形都写死了。
  选「关实时保护」当兜底、而不是加排除项的理由：一线自己能做完，
  不必为一次铺设去改机器安全策略，也不用等谁拍板。
  ⚠️ **代价一条都没消失**：重启后 Defender 会把实时保护**自动开回来**，
  那时第 12 步重新变红、取包重新被拦 —— 现场表现是「昨天还好好的，今天又坏了」。
  遇到就回清单第 3.5 步复探、按 1→2→3 走，**别去改 fetch**。
  想一劳永逸（重启也不反弹）只有下面排除项那条路，但它要拍板。
- **根治只能从环境下手**：加 Defender 排除项。**用脚本，别手敲** ——
  手敲容易漏、容易加错、也不可回滚：

  ```powershell
  # 先看它打算做什么（不改任何设置）
  powershell -NoProfile -ExecutionPolicy Bypass -File tools\add_av_exclusions.ps1 -DryRun
  # 确认没问题再加（要管理员）
  powershell -NoProfile -ExecutionPolicy Bypass -File tools\add_av_exclusions.ps1
  # 反悔就删掉（只删它自己加的那几条，精确匹配）
  powershell -NoProfile -ExecutionPolicy Bypass -File tools\add_av_exclusions.ps1 -Remove
  ```

  它加的是**本项目相关的几条**：仓库目录、`installer_dir`、本机 `%TEMP%`、
  以及 `python.exe` 进程 —— 不碰整个 C 盘、不动组策略，幂等且可回滚。
  加完复跑一次探针，应当**没有 225**。

  ⚠️ **这是安全策略变更，会削弱这台机器的防护，别私自铺开**：
  **默认不跑、bootstrap 也不会自动跑**（不放进 12 步里）。
  要不要在 5 台 / 20 台上统一加，由人拍板。
  顺带一提，这台机器上**还装着 McAfee**（`SecurityCenter2` 里两个 AV 并存），
  本脚本只管 Defender —— McAfee 那边要在它自己的控制台里加。

#### ⚠️ 坑 7：子进程输出中文就报 `UnicodeDecodeError`，**报错内容整句丢失**（2026-09-21 修）

**现象**（首台真机 DESKTOP-DOHED68 跑 bootstrap 时）：

```
Exception in thread Thread-21 (_readerthread):
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xb4 in position 0: invalid start byte
Exception in thread Thread-22 (_readerthread): ... 0xbe ...
Exception in thread Thread-23 (_readerthread): ... 0xb3 ...
```

三条一起冒，看着像网络/共享盘坏了，其实**只是解码猜错**。

**根因**：包装脚本 `tools/bootstrap_machine.ps1` 设了 `PYTHONUTF8=1`，
于是 `locale.getpreferredencoding(False)` 变成 **utf-8**；而 Windows 自带命令
在中文系统上吐的是 **ANSI(cp936)**（`net use`、`schtasks /Create`、`icacls`），
`schtasks /Query /XML` 更是 **UTF-16LE**。
`subprocess.run(..., text=True)` 的 TextIOWrapper 按 utf-8 解这些字节 → reader 线程抛异常死掉
→ **`proc.stdout` 变成 `None`** → `(proc.stdout or proc.stderr or "")` 拿到空串
→ **那一句报错永远看不到内容**。

**最坑的一处**：`_task_action()` 读 `schtasks /Query /TN HallAutoP1 /XML`。
读不到 XML 就返回 `""`，调用方当成「本机还没有这个任务」→ 走 `/Create /F`
**把已存在的计划任务强制重建，正好重置触发时间** ——
而 `step_schtask` 的 docstring 明说这件事不许发生（跑批中重建会抹掉任务状态）。
**第二次跑 bootstrap 的机器上就会踩**。

**已修**：`tools/bootstrap_machine.py` 里所有文本模式子进程统一走 `_run_text()`：
先收字节，再由 `_decode_console()` 按 **UTF-16 BOM → utf-8 → 本机 ANSI** 顺序解码。
回归锁：`tests/unit/test_bootstrap_policy.py` 的 `test_decode_console_handles_gbk_and_utf16`、
`test_run_text_decodes_real_gbk_child`、`test_no_text_mode_subprocess_left`（源码守卫，禁止再用 `text=True`）。

**排查提示**：见到 `UnicodeDecodeError ... in _readerthread` 别去查网络，
那是**本机代码在解子进程输出**；先看那句 `0x??` 是不是 GBK 双字节首字节。

#### 排错对照表（实测）

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| `dir` 无任何输出（不报错） | **目录是空的**，不是失败 | 放个文件再试 |
| 路径不存在（`Get-ChildItem` 报 ItemNotFound） | 网络层没通（防火墙）或凭据没建立 | 先 `ping`，再 `Test-NetConnection -Port 445` |
| 找不到网络路径 | 防火墙挡 445 | 放行 445 |
| 输入的凭据无效 | 用了空密码账号 | 建带密码的专用账号 |
| 拒绝访问 | 共享权限没给对 | `Grant-SmbShareAccess` |
| 拒绝访问，但权限明明是对的，且**偶发** | 杀软/索引服务的瞬时句柄锁（WinError 5/32） | 已由 `_atomic_replace` 重试覆盖；还报就是真 ACL 问题 |
| `[Errno 22] Invalid argument`，文件是**本进程刚写的** | **杀软把刚写的文件判毒**（`GetLastError=225`，见坑 6） | 先跑 `tools\probe_av_quarantine.py` 确认；**现阶段按《新机操作清单》步骤九关掉实时保护**（跑批期间保持关着，整机不再跑批再开回来）。重启后会被自动开回来，重新关一次即可。想重启也不反弹用 `tools\add_av_exclusions.ps1`（安全策略变更，需拍板） |
| 控制台刷 `_readerthread` 的 `UnicodeDecodeError` | 本模块用 `text=True` 解了 cp936/UTF-16 输出（见坑 7） | 已修；新加子进程调用走 `_run_text()` |
| ping 不通 | AP 隔离或不同网段 | **这条路死了**，换 U 盘 |

#### 与代码的衔接（已接通，2026-09-18）

`hall_auto/fetch.py` 的查找链已包含共享盘：**本地 → 缓存 → 共享盘 → 下载**。
只要在 `config.yaml` 填上共享盘地址，脚本就会自动从共享盘取包，不用手工 `net use`。

```yaml
package_share:
  dirs:
    - "//LAPTOP-VS5F7HF4/hall-packages"
```

**注意：脚本读的是 UNC 路径，不是映射盘符。** 映射盘符（`Z:`）在计划任务/服务里
通常不可见（不同的登录会话），UNC 路径没有这个问题。所以配置里写 `//host/share` 形式。

**访问凭据怎么给脚本？** `bootstrap_machine.py` 的「共享盘连接」步骤会自动连，凭据走环境变量：

```powershell
$env:HALL_SHARE_USER="hallshare"
$env:HALL_SHARE_PASSWORD="<密码>"
powershell -NoProfile -ExecutionPolicy Bypass -File tools\bootstrap_machine.ps1
```

它会执行 `net use \\host\share <密码> /user:<账号> /persistent:yes`，**重启后自动重连**。
不想让它碰共享盘就加 `--skip-share`。

也可以手工连（效果一样）：

```powershell
net use \\LAPTOP-VS5F7HF4\hall-packages /user:hallshare "<密码>" /persistent:yes
```

**凭据只走环境变量**（红线：不落盘、不进 git）。

**注意：脚本读的是 UNC 路径，不是映射盘符。** 映射盘符（`Z:`）在计划任务/服务里
通常不可见（不同的登录会话），UNC 路径没有这个问题。所以配置里写 `//host/share` 形式。

**实测验证过的场景**（2026-09-18）：

| 场景 | 结果 |
| --- | --- |
| 共享盘可达、有包 | `source=share`，拷进 `_cache`，sha256 校验一致 |
| 第二次取同一个包 | `source=cache`（不再走网络） |
| 本地有包 | `source=local`（不碰共享盘） |
| 共享盘不可达 | 5s 超时后判定不可达，**自动降级下载**，不报错 |
| 共享盘有包但 sha256 不符 | 报错（不静默用坏包） |
