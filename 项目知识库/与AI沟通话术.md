# 用 AI 做自动化：沟通话术与经验

> 最后更新：2026-10-28
> 用途：这次华硕大厅客户端 UI 自动化是怎么让 AI 一步步做出来的，给组内做参考 ——
> 照着这套打法做 UI 自动化、接口自动化都适用。**不是工具教程，是沟通方法。**
> 项目现状：287 个 commit（09-02 出方案、09-03 起写代码）、35 条功能用例、926 条单元守卫、
> 可多机无人值守跑批。

---

## 一句话总结

**AI 会写代码，但不知道你的产品长什么样、也不知道你上次踩了什么坑。**
所以我的活儿不是"让它写脚本"，而是**把两样东西喂给它并且持续维护**：

1. **产品事实** —— 控件叫什么、接口返回什么、哪一步会弹窗（我们叫「探壳」）；
2. **踩过的坑** —— 每个坑修完都固化成一条守卫测试，让它下次改不坏。

这两样一旦落进仓库文档和测试里，AI 换一茬、对话清空，进度也不丢。

## 二、六个阶段：我说什么，AI 做什么

### 阶段 1 · 先出方案，不写代码

**我说**：把产品情况、要测什么、机器限制讲清楚，让它出一份方案：范围分层、技术栈、
版本口径、哪些明确**不做**。关键决策我自己拍板，它只给选项和代价。

**产出**：`主流程自动化设计.md` —— 里面「已对齐结论」表把 12 个决策钉死
（比如"能读系统状态就不要点 UI"、"MuMu/微信小程序本期不测"、"破坏性操作可逆且范围小"）。

**为什么值得**：后面 287 个 commit 里，AI 每次要动手前都能拿这份对一遍，不会跑偏。
**没有这一步的话，AI 会直接开写，然后你会得到一串很长的脚本，改不动也不敢删。**

> 💬 话术：「先别写代码。按我说的情况出一份方案：范围分层、技术选型、风险。
> 每个有争议的地方给我 2-3 个选项和各自代价，我来定。」

### 阶段 2 · 探壳：让 AI 先把产品摸清楚

这是**最省时间的一步**，也是最容易被跳过的一步。

**我说**：别猜控件名，写个探针把真实的控件树打出来，我们照着实测结果写断言。

**AI 做**：写了 `tools/probe_uia.py` / `probe_win32.py` / `probe_installer.py`，
把每个页面的控件（aid、类型、名字）dump 出来。

**产出**：`项目知识库/探壳结论.md` —— 控件图 + 定位坑 + oracle 口径。
**规矩是：写任何断言之前必须先读这份。**

**探出来的东西有多值钱**（都是猜不到的）：

- 登录后主窗口的 UIA 名字**从「华硕大厅」变成「华硕应用商店」**（Win32 标题不变）
  → 按名字匹配的话，登录态下所有操作必然失败，而且报错是"元素找不到"，看不出是改名了；
- 搜索框是原生 `Edit`、WebView2 内容 UIA 可读 → **不需要上 Playwright**，省掉一整套技术栈；
- 首跑会先弹一个独立的「权限确认窗口」，点完同意主窗口才出现；
- 大厅会**恢复上次的页面**（可能落在设置页）→ 就绪判定必须包含"回首页"。

> 💬 话术：「不要猜控件名。先写个只读探针，把 <某页面> 的控件树打出来（aid、类型、名字、位置）。
> 结果整理成一份控件图文档，以后写断言都以它为准。」

### 阶段 3 · 分层落地：P0 跑通再动 P1

**我说**：按方案里的 P0（冒烟）→ P1（各模块）→ P2（安全/入口）顺序做，**每层真机跑绿了再下一层**。

**关键约束**（这几条是我提的，AI 照着实现）：

- **能读系统状态就不点 UI**：版本号读注册表和文件版本，已装应用读卸载项，UI 只验"人看得到的那层"；
- **有副作用的流程做成可逆往返**：改密码 → 用新密码登进去验 → **再改回来**，还原放 `finally`；
  装夹具 → 验注册表有条目 → 卸掉 → 验条目消失。**不许停在"点了按钮没报错"这种安全中间步**；
- **数据依赖全部夹具化**：搜索词、可更新应用、账号都进配置，运营一变只改配置不改脚本。

> 💬 话术：「这条用例不许停在'点了没报错'。要验真实结果：做完 → 断言效果 → 还原回原状态，
> 还原放 finally。跑完机器要跟跑之前一样。」

### 阶段 4 · 真机跑批 → 修 → **加守卫**（这一步是核心）

从单机跑通到多机无人值守，中间修了几十个问题。**每个问题的处理方式都一样，三步：**

1. **先做出会复现的检测**（不猜）；
2. 修根因，不打补丁绕过；
3. **加一条常驻守卫测试**，让它以后改不回去。

926 条单元测试里，绝大多数是这种守卫 —— 它们不启动客户端，只锁"框架本身的规则"。

**几个真实例子：**

| 踩的坑 | 守卫怎么钉 |
| --- | --- |
| 插 helper 插到了装饰器和 `def` 之间 → 标记挂错，用例**一条不跑还不报错** | 每条 `def test_*` 必须带套件标记 |
| 发放文档里写死了第一台测试机的名字 → 一线照抄，任务投给了旧机器，两边都不报错 | 文档里只许出现常量机器名，出现具体测试机名就报红 |
| `reports/` 在 .gitignore 里，本机碰巧有、新机没有 → 本机绿、每台新机 219 条 ERROR | 隔离参数改成函数，进去先建父目录 |
| 文档里的套件表和代码漂了 → 有人投一个不存在的套件 | 表的每一行必须与 `suites.py` 一致 |
| 手册让人在 bootstrap 之前用 `.venv`（那时还没建出来） | 扫文档代码块，`.venv` 只能出现在 bootstrap 之后 |

**注意最后两条：连文档都有守卫。** 文档漂了不会报错，但它让一线白干半天，所以照样钉住。

> 💬 话术：「这个问题修完之后，加一条守卫测试，让它以后不可能再犯。
> 守卫写完**故意制造一次违规**，确认它真能红 —— 只会绿的守卫是安慰剂。」

### 阶段 5 · 让失败自己说话

无人值守跑批最大的成本是**"红了但不知道为什么"** —— 一次农场往返就是几十分钟到几小时。
所以我提了一条硬要求：**每个失败点都必须留证。**

**AI 照做的结果**：

- 每条用例跑完留一张原图（通过也留），失败留控件树 + 窗口句柄诊断；
- 报错文本里带**现场事实和原始数字**，不只给结论：
  不说"登录超时"，说"窗内文案是 X、大厅被 Y 挡住、cloaked=1、alpha=0"；
- 报错按原因**分流**：窗口被挡 → 告诉你把窗口处理好重跑；`alpha=0`（窗口完全透明）
  → 直接标"产品侧问题，报开发，别在环境上打转"。

**这条的回报极大**：有几次红，我看报错文本就直接定性了，不用再跑一轮。

> 💬 话术：「这个 raise 点报错里必须带现场事实：当前窗口状态、控件树摘要、原始数字。
> 别只给结论 —— 结论和现象矛盾的时候我没法定性。」

### 阶段 6 · 用例数据化：让"改用例"不用懂代码

**起因**：组长要求"用例可以单独拿出来、增删改直接在用例上操作、脚本只负责读取"。

**AI 给的答案很实在**（这点我很认可）：**能做，但不能全做。**
当时 36 条用例里只有 13 条能纯数据驱动，剩下 23 条（登录、装卸、主题切换）硬搬进 YAML
会得到一个表达力不足的自制小语言，维护成本更高。

**落地方案**：`cases/cases.yaml` 是**唯一真源** → 导出器出 md/CSV/禅道 JSON/Word
→ 双向守卫钉住"清单和代码不许漂"。现在改一条用例的名字、验证点、加一组参数，只动 YAML。

> 💬 话术：「我要 <某个能力>。先告诉我哪些能做到、哪些做不到、做不到的代价是什么，
> 别硬做。方案我评审完你再动手。」

## 三、话术速查表（可以直接抄）

| 场景 | 发给 AI 的话 |
| --- | --- |
| 新对话开场 | 「你在 <项目名> 里干活。先读根目录《会话交接.md》和 `AGENTS.md`，搞清楚当前进度和红线再动手。」 |
| 起步 | 「先别写代码，出方案：范围分层、技术选型、风险。有争议的地方给我选项和代价，我拍板。」 |
| 摸清被测对象 | 「不要猜。写个只读探针把真实的 <控件树 / 接口响应> dump 出来，整理成文档，以后以它为准。」 |
| 写断言 | 「断言要验真实结果，不许停在'调用了没报错'。有副作用就做成可逆往返，还原放 finally。」 |
| 修 bug | 「先做出会复现的检测，再假设，再修根因。别加 try/except 绕过。」 |
| 修完之后 | 「加一条守卫测试钉住它，然后故意违规一次，确认守卫真能红。」 |
| 报错难查 | 「报错里带现场事实和原始数字，不要只给结论。」 |
| 它说"环境坏了" | 「先做证伪实验再下结论。你说跑不了，把跑的过程和原始输出贴出来。」 |
| 它说"改好了" | 「给我证据：测试输出、日志路径、截图。别只给结论。」 |
| 配置类改动 | 「这个值要面向所有测试机，不许写我这台机器的具体路径/名字。」 |
| 文档改动 | 「改完跑守卫测试，再重出发放版。文档漂了不会报错，所以必须有守卫。」 |
| 它顺着我说不好的方案 | 「别一味附和我。我这个方案有坑就直接指出，给替代做法。」 |

⚠️ **一条安全红线**：密码、测试账号、令牌**绝不进对话、不进任何文件**（含 git）。
只走环境变量或已 gitignore 的本地配置文件。要发出去的文档里写占位符，
生成发放版时由脚本从环境变量现场替换（我们用的是 `tools/sync_handbook.py`）。

## 四、几条最值钱的经验

1. **假绿比红灯更坏。** 这个项目反复治的就是这一类：用例被静默跳过、任务投了没人取、
   本机绿新机红、守卫只会绿不会红。**红灯你会去看，假绿你会当成"没问题"发出去。**
   → 所以每次改完测试文件都对一次收集数量，守卫都要验过能红。

2. **"本机跑得通"推不出"别处跑得通"。** 本机碰巧有的东西（`.venv`、gitignore 掉的目录、
   配好的 `config.local.yaml`、常驻环境变量、已认证的共享盘）正好把新机的坑全盖住。
   → 验收前**先把这些删掉再跑**；文档和配置里**不许出现具体某台机器的值**。

3. **"没消息"不是"没问题"。** 长任务的进度要落在**别人看得见的地方**。
   我们的提权段最长会安静等 4 小时，进度只打在自己的终端上，控制机看到的和"节点死机"一模一样。
   → 进度写共享日志 + 查询接口**带时长**（"刚投 3 秒"和"跑了 59 分钟"必须能区分）。

4. **AI 会顺着你，你要主动要求它反驳。** 我明确跟它说过"别一味附和，我有坑你就指出来"。
   后面它拦过我好几次（比如用例数据化那次"能做但不能全做"）。
   → 不问的话，它会把你错误的假设一路实现下去，做出来才发现前提就是错的。

5. **问之前先确认前提假设。** 有一次我担心"20 台并发打服务端会不会限流"，还准备了话术请组长转发。
   后来发现组长说的是"一批 5 台" —— **问题根本不存在**，是我拿着没验证的假设推导出一堆风险。
   → 让 AI 帮你查清前提，比让它帮你措辞更有用。

6. **文档要分层，不然一定会烂。** 我们分三层：
   《会话交接.md》只放**会变的**（进度、下一步、未提交清单，有字数上限）；
   `项目知识库/` 放**稳定的**（控件图、坑、跑法、决策）；
   一次性过程叙事（第几轮复跑、耗时、commit 号）归 commit message。
   → **同一条事实只留一个权威来源。** 三层混在一起的话，新对话读起来是流水账，找不到重点。

## 五、迁移到接口自动化的建议

这套打法里，**跟 UI 无关的部分全都能直接用**：

| UI 自动化里我们做的 | 接口自动化对应什么 |
| --- | --- |
| 探壳：dump 控件树 | **抓真实响应**：拿一份真返回存成 fixture，别照着接口文档猜字段 |
| 控件图 + oracle 口径 | **响应字段图**：哪些字段稳定、哪些易变（时间戳/文案）、哪些是 null 语义 |
| 能读系统状态就不点 UI | 能直接查库/查状态就不断言响应文案 |
| 可逆往返 | **造的数据要能清掉**：建 → 验 → 删 → 验删干净，删除放 `finally` |
| 夹具应用 | 测试账号、测试数据全部夹具化进配置，环境一变只改配置 |
| 失败留证 | 失败时留**完整请求 + 完整响应 + 耗时**，别只留 assert 那一行 |
| 用例清单唯一真源 | 同一份 YAML/表格出用例清单、出禅道、出报告，守卫钉住不许漂 |

**接口自动化会更容易的地方**：没有窗口遮挡、DPI 缩放、控件改名、UAC 提权这些环境噪音，
稳定性会高一个量级。**但"假绿"这一类问题一模一样**，甚至更隐蔽 ——
mock 了外部依赖，mock 和真实响应漂了，测试全绿而线上挂。
→ 建议：**关键路径至少保留一组打真实环境的用例**，别全 mock。

**建议起步顺序**（照我们这条路，能省掉大量返工）：

1. 先出方案（范围分层 + 明确不做什么），人拍板；
2. 抓真实响应做"探壳"，落一份字段文档；
3. 挑一条主流程做**可逆往返**，跑绿；
4. 铺开到各模块，每条失败都带现场；
5. **每修一个坑加一条守卫** —— 这是回报率最高的投入；
6. 最后再做用例数据化和多机/CI。

⚠️ 别一上来就搭框架、上 CI、搞数据化。**我们是跑到第 4 步才发现需要守卫，
第 6 步才被要求数据化** —— 顺序反了会做一堆用不上的抽象。

## 六、代价（也说清楚）

- **守卫测试是要维护的。** 926 条单测跑一次 50 秒，改套件定义时守卫会红，得跟着改。
  但比起"改坏了没人知道"，这个代价值得。
- **文档三层分工需要人盯。** 交接文档有字数上限，超了要手动归档，这活儿 AI 能帮你做但得你发起。
- **探壳结论会过期。** 换版本、换机器都要复核 —— 我们在文档头部写了"最后更新"和"来源：本机实测"，
  就是为了让人一眼看出它可能旧了。
- **不是所有东西都能自动化。** 人在环（收短信码）永远需要真人；
  我们做成"自动段跑完再问一句要不要参与"，不参与就记带原因的 skip，**不假装它通过了**。
